Every table here does one of three jobs: organize books, save words, or share definitions between users.

None of it is generic CRUD boilerplate. If a column looks strange, there is a reason for it. This page explains the reasons, not only the shapes.

The schema files are in `packages/db/src/schema/`. There is one file per group of tables. They are all re-exported from `schema/index.ts`.

## Tables owned by Better Auth

Better Auth creates and manages four tables: `user`, `session`, `account` and `verification` (`schema/auth.ts`). See [Authentication](/docs/authentication).

Treat these tables as a black box. `user.id` is the anchor for every other table, but our code never writes raw queries against `session` or `account`.

## Organizing what you read: `book` + `folder`

```ts
// schema/book.ts (shape)
book: { id, provider, externalId, title, authors[], coverImageUrl, description, pages? }
folder: { id, userId, bookId?, title, status: "reading" | "finished" | "misc", currentPage? }
```

### `book`

`book` is a **cache**. It stores book information that we copied from an outside API (see [Book search](/docs/book-search)).

Two details matter:

- `provider` and `externalId` are plain `text` columns, not a Postgres enum. This is on purpose. Today the only source is Hardcover. But text means we can add or change providers later without writing a database migration. The two columns together have a unique index. That unique index is what lets `folder.create` insert-or-update safely, even if two people pick the same book at the same time.
- There is no `raw jsonb` column and no `topics[]` column. Both were deleted. `raw` stored a copy of data we can fetch again with one API call. `topics` was for an AI feature that does not exist. A column you keep "just in case" still costs storage and still has to be migrated forever. Add such a column back on the day you add the feature that reads it.

### `folder`

A `folder` is one shelf for one user. It means "I am tracking this book."

`bookId` can be null. This is intentional: a folder does not need a real book. A freeform list (for example, "words from podcasts") is a normal case, not an edge case.

`title` is copied from the book when the folder is created. This is a small duplication, but it lets the home screen list all folders without joining the `book` table every time.

`currentPage` is where this reader is in the book. A saved word with a `page` moves it forward, never back, so a word from a flashback page leaves it alone. `folder.update` can set any page, for a re-read. `book.pages` is Hardcover's count for one edition, so it only scales the progress bar; a page past it is allowed and the bar stops at 100%.

A simple way to picture it: `book` is one shared page per book, like a Wikipedia article. `folder` is one personal notebook, per user, per book.

## The main table: `word`

```ts
// schema/word.ts (shape)
word: {
  id, userId, folderId, bookId?,
  term, normalizedTerm,
  dictionaryEntryId?, definitionOverride?, personalNote?,
  captureMethod: "manual" | "voice",
  page?,
  contributesToAggregate, mastered, masteredAt?, lastReviewedAt?,
}
```

One row is created every time a user saves a word. Many of these columns exist because of a product decision, not only because of a data type.

### `term` and `normalizedTerm`

`term` keeps exactly what the user typed or said, for example `"Ubiquitous"`.

`normalizedTerm` is the lowercase, trimmed version, for example `"ubiquitous"`. We use it for matching, for removing duplicates, and for grouping.

The rule is simple:

- **Display** `term`.
- **Search and join on** `normalizedTerm`.

Only one function creates that normalized form: `normalizeTerm` in `@better-vocab/domain`. Everything that matches a word to a definition calls it — the two routers, the app's resolver, and the script that builds the offline dictionary file.

This function used to be copied by hand in all four places. That was dangerous. If the build script and the app had disagreed by even one character, every offline lookup would have failed, and nothing would have shown an error. See the [changelog](/docs/changelog).

### Why `userId` and `folderId` are both on `word`

`folder` already has a `userId`, so we could find the owner with a join. We store it twice anyway.

This is called denormalization: copying data on purpose to make a common query faster. "Show me all my words from every folder" is a very common query. With `userId` on the row, it never needs a join just to check who owns the word.

### Why `bookId` is on `word` too

`bookId` is copied from `folder.bookId` at the moment the word is created. It follows the same idea, one level higher.

The crowdsourced query asks: "which words did any user save for this book, in any of their folders?" With `bookId` on the row, that query does not need to join `folder` either.

Two indexes support this:

- a unique index on `(folderId, normalizedTerm)` — used for the duplicate check inside one folder
- an index on `(bookId, contributesToAggregate)` — used for the crowdsourced query

### `dictionaryEntryId` can be null

Null means "we do not have a definition yet". This is the pending state after an offline capture. The word row exists first, and a real definition is attached later, when one is found.

### `personalNote` and `definitionOverride`

Both hold text on one user's copy of a word, but only one of them is written by the reader:

- `personalNote` is the reader's own words, and sits **next to** the definition. It is the only text a reader can write.
- `definitionOverride` is the definition the phone showed when the word was saved. It is kept only when the server had no shared entry yet, and no procedure edits it: **definitions are not user-editable**.

That difference is the reason both exist. A note is always private, because no crowdsourced result has a column that could carry one. Spoiler safety is built into the shape of the data, so no developer has to remember a rule.

### Review state

`mastered`, `masteredAt` and `lastReviewedAt` hold the review state.

The server writes both timestamps itself. `word.update` takes `mastered` and `reviewed: true` from the client, and then stamps the dates. It never accepts a date from the client. So a phone with a wrong clock cannot backdate a review.

That procedure also writes only the fields it received. So finishing a flashcard cannot erase a note that was typed on the same row.

### `contributesToAggregate` is a snapshot

This column is copied from the user's settings at the moment the word is saved. We do not read the current setting later.

Why copy instead of read live? Imagine a user turns the setting off next month. A word they saved three months ago should not suddenly disappear from other people's crowdsourced view. And it should not come back if they turn the setting on again.

It is the same idea as saving the price on an order. You store the price the customer paid, not today's price.

## Why definitions have their own table: `dictionaryEntry`

Here is the question to think about. If 500 users look up the word "ephemeral", should we store that definition 500 times?

```ts
// schema/dictionary.ts (shape)
dictionaryEntry: { id, term (unique), definition, contexts[], exampleSentence?, usageNote?, source: "bundled" | "dictionary_api" | "ai_enhanced", enrichedAt? }
```

No. `dictionaryEntry` is a **shared cache**: one row per unique term, with no link to any user.

The first time the server resolves "ephemeral", it saves the row here. Every later request for that word is answered from this table. No second API call, and no second cost.

<Callout type="warn">
**Only the server may write this table.**

`word.create` accepts a `definition` from the phone, but it saves that text on the user's own `word.definitionOverride`. It never writes `dictionaryEntry`.

This is the privacy rule the whole product depends on: users share **how often a word was saved**, never **what it means**. If a client could write the shared row, the first person to save a word would define it for every other reader, forever, with no way to fix it. `db:smoke` checks this rule directly.
</Callout>

Because of that rule, `word.dictionaryEntryId` stays null until server code fills it. Each phone answers its own lookups from the offline dictionary, or from the server's shared row when it is online.

`term` in this table holds the **normalized** form. It is a match key, not a display string. Any query that joins to this table must normalize first. Joining with `"Serendipity"` matches nothing, and you get no error.

### The AI columns

`exampleSentence`, `usageNote` and `enrichedAt` live on this shared row, for the same reason the definition does. The cost rule is that **each unique word triggers at most one AI call for the whole user base**. Enrich once, serve forever.

`enrichedAt` has two jobs. It records when enrichment ran, and it acts as a lock. Two lookups of a new word at the same time buy only one enrichment between them. See [AI enrichment](/docs/ai-enrichment).

There used to be a per-word example sentence column as well. It was removed. One shared row is the whole point, and having both created an extra branch in two screens for a case nobody asked for.

### `contexts`

`contexts` is a `text[]` of invented sentences. The term is marked with braces:

```
"The house had an {eldritch} stillness about it."
```

It is an array, not its own table, for the same reason `book.authors` is an array. It holds two or three short strings. We always read them with the row, and we never query one alone. A join would buy nothing.

Because these sentences are shared and keyed by term, the [quiz](/docs/api-layer#wordquiz) built from them costs no extra AI call. See [AI enrichment](/docs/ai-enrichment#contexts-and-the-fill-in-the-blank-card) for what the braces do.

### Reading a definition

`word.definitionOverride` is the other half of the privacy rule. It holds the definition the phone showed when the word was saved, usually from its offline dictionary. A reader cannot type or edit one; their own words go in `personalNote`. Only that one user ever sees it.

Screens always read:

```ts
word.definitionOverride ?? word.dictionaryEntry?.definition
```

### One definition per term

`dictionaryEntry` stores exactly **one** definition per term, even though many words have several senses ("bank" the building, "bank" the side of a river).

This table means "the best answer we have", not "a full dictionary". Multiple senses are handled on the phone instead (see [Offline dictionary](/docs/offline-dictionary)), because the offline WordNet data is static reference data with no server version.

The real match for this table is the `cached` rows in the phone's own `dictionary` table, and those are also one row per term. So the two designs already agree. This is a decision, not a mistake.

## Settings: `userPreference`

```ts
// schema/preference.ts (shape)
userPreference: { userId (PK), contributeToAggregateByDefault, offlineDictionaryTier: "core" | "extended" }
```

This is a 1:1 side table for app settings. We keep it separate from `user` instead of adding columns to `user`.

The reason: Better Auth owns and migrates the `user` table. If we add our own columns there, one of its future migrations will eventually conflict with ours.

`preference.get` and `preference.update` ([API layer](/docs/api-layer#the-preference-router)) are the only way in.

For a long time this table had a reader and no writer. `word.create` read `contributeToAggregateByDefault`, but nothing could change it. So the opt-out was impossible to use in practice.

The default values live in `@better-vocab/domain` as `PREFERENCE_DEFAULTS`. That one definition is used in two places:

1. as the Postgres column defaults
2. as what `preference.get` returns for a user with no row yet

So reading preferences never creates a row.

There used to be a `pushToken` table here, for a weekly digest email. It was deleted. No code anywhere sends a push notification, and registering Expo tokens takes a few minutes whenever the digest is really built. Same rule as `book.raw`: a table that nothing writes to is a cost, not a head start.

## How it all connects

```
user ──┬── folder ──── book
       │      │
       │      └── word ──┬── dictionaryEntry   (shared: many words point to one entry)
       │                 └── (denormalized userId + bookId, see above)
       └── userPreference (1:1)
```

## Example: saving one word

A user has a "Dune" folder. They save the word "ornithopter". Here is what `word.create` does (see [API layer](/docs/api-layer) for the procedure itself):

1. Check that the "Dune" folder belongs to this user. Read its `bookId` from the same row, while we are already there.
2. Normalize the term to `"ornithopter"`.
3. Look for an existing `"ornithopter"` row in `dictionaryEntry`. This step is **read only**. Someone else has probably looked this word up already, so we link to the shared row if it exists. If it does not exist, any definition sent with the request is stored on **this user's** `definitionOverride`. Saving a word never writes the shared table. Only `dictionary.lookup` does.
4. Read this user's `userPreference` and snapshot their aggregate opt-in setting. If they have no row, use `PREFERENCE_DEFAULTS`.
5. Insert the `word` row: `userId`, `folderId`, `bookId`, the term, the `dictionaryEntryId` (or null), and the snapshot. If a row with this `(folderId, normalizedTerm)` already exists, the insert does nothing and we return the existing row.

Later, the crowdsourced view for "Dune" runs a query like this:

```sql
SELECT normalized_term, COUNT(DISTINCT user_id)
FROM word
WHERE book_id = 'dune-id' AND contributes_to_aggregate = true
GROUP BY normalized_term
ORDER BY count DESC;
```

This is the query that the `bookId` copy and its index exist for.

<Callout>
There is deliberately **no** `book_word_aggregate` counter table. One existed, and it was deleted.

A counter counts captures, not people. One user with the same word in ten folders would look like ten readers. Keeping a counter correct also means getting four separate paths right: increment on create, decrement on delete, opt-out changes, and folder cascades.

`COUNT(DISTINCT user_id)` is smaller code and a more correct answer. Add a counter back only when this query appears in slow query logs.
</Callout>

The list is also computed fresh every time, never cached. A stale cached list could show old results, and old results can contain spoilers.

That query is `word.suggestions` ([API layer](/docs/api-layer#wordsuggestions)). It adds two filters to the shape above: it removes your own words, and it removes words already in the folder you are viewing. It returns counts only, with no definition text.
