Every table here exists to serve one of three needs: organizing books, capturing words, or sharing definitions cheaply across users. None of it is generic CRUD boilerplate — if a column looks unusual, there's a reason, and this page tries to explain the reason rather than just the shape.

Schema files live in `packages/db/src/schema/`, one file per domain group, all re-exported from `schema/index.ts`.

## Tables owned by Better Auth

`user`, `session`, `account`, `verification` (`schema/auth.ts`) are generated and managed by Better Auth — see [Authentication](/docs/authentication). Treat them as a black box: `user.id` is the anchor every other table hangs off of, but application code never writes raw queries against `session`/`account` directly.

## Organizing what you're reading: `book` + `folder`

```ts
// schema/book.ts (shape)
book: { id, provider, externalId, title, authors[], coverImageUrl, description }
folder: { id, userId, bookId?, title, status: "reading" | "finished" | "misc" }
```

**`book`** is a *cache* of metadata pulled from an external book API (see [Book search](/docs/book-search)). Two things worth noticing:

- `provider` and `externalId` are plain `text`, not a Postgres enum. That's deliberate — the metadata source is still just Hardcover today, but keeping it as text means adding or swapping providers later never requires a schema migration. The pair is uniquely indexed, which is what makes `folder.create`'s upsert idempotent.
- There is no `raw jsonb` column holding the unparsed upstream response, and no `topics[]`. Both were dropped: `raw` stored a copy of something re-fetchable in one API call, and `topics` fed an AI suggestion feature that doesn't exist. Columns kept "just in case" are rows you pay to store and migrate forever — add them back with the feature that reads them.

**`folder`** is a user's personal shelf entry — "I'm tracking this book." `bookId` is nullable on purpose, because a folder doesn't have to be tied to a real book (freeform/misc lists are a supported case, not an edge case). `title` is copied from the book at creation time — a small denormalization so the home screen can render a list of folders without joining to `book` on every load.

Think of `book` as one shared Wikipedia-style page per book, and `folder` as one personal binder per user per book.

## The core entity: `word`

```ts
// schema/word.ts (shape)
word: {
  id, userId, folderId, bookId?,
  term, normalizedTerm,
  dictionaryEntryId?, definitionOverride?, personalNote?,
  captureMethod: "manual" | "voice",
  contributesToAggregate, mastered, masteredAt?, lastReviewedAt?,
}
```

This is what gets created when a user taps "+ Add word." Several columns encode a real product decision, not just a data type:

- **`term` vs. `normalizedTerm`** — `term` preserves exactly what the user typed or said ("Ubiquitous"); `normalizedTerm` is the lowercased/trimmed form ("ubiquitous") used for matching, deduping, and grouping. Always *display* `term`; always *search or join on* `normalizedTerm`.

  That normalized form is produced by exactly one function, `normalizeTerm` in `@better-vocab/domain`, and everything that matches a word to a definition goes through it — the two routers, the app's resolver, and the script that stamps the bundled dictionary at build time. It was written out inline in all four places until recently; a drift between the build script and the runtime lookups would have made every offline lookup miss silently. See the [changelog](/docs/changelog).
- **`userId` and `folderId` both live on `word`**, even though `folder` already has a `userId` you could join through. This is intentional duplication (denormalization): "show me all my words across every folder" is a common query, and this way it never needs a join just to check ownership.
- **`bookId` follows the same logic, one level up.** It's copied from `folder.bookId` at the moment a word is created, so the crowdsourced-discovery query ("every word logged against this book, by any user, across all their different folders") doesn't need to join through `folder` either. There's a unique index on `(folderId, normalizedTerm)` and a lookup index on `(bookId, contributesToAggregate)` specifically to make both the per-folder dedup check and this aggregate query fast.
- **`dictionaryEntryId` is nullable** — that's the "pending definition" state from offline capture. The word exists before a real definition does; it gets attached later once one resolves.
- **`personalNote` sits *alongside* the definition; `definitionOverride` replaces it.** That's the whole difference between the two, and it's why both exist. A note is private by construction — nothing in the crowdsourced result could carry one, which is what makes spoiler safety structural rather than a convention someone has to remember.
- **`mastered`/`masteredAt` and `lastReviewedAt` are the review state**, and the server owns both timestamps: `word.update` stamps them from `mastered` and `reviewed: true` rather than accepting a date from the client, so a device with a wrong clock can't backdate a review. Every field of that procedure is written only when sent, so a flashcard turn can't blank a note typed on the same row.
- **`contributesToAggregate` is copied from the user's settings at the moment the word is created**, not read live from their current settings every time. Why copy instead of reference? Because if someone flips their opt-out setting next month, a word they logged three months ago shouldn't retroactively vanish from (or reappear in) other people's crowdsourced view. It's a snapshot in time, not a live flag — the same reasoning you'd apply to storing a price at the time of purchase rather than looking it up fresh every time you view an old receipt.

## Why definitions live in their own table: `dictionaryEntry`

Here's the question worth sitting with: if 500 users all look up the word "ephemeral," should the definition be stored 500 times?

```ts
// schema/dictionary.ts (shape)
dictionaryEntry: { id, term (unique), definition, exampleSentence?, usageNote?, source: "bundled" | "dictionary_api" | "ai_enhanced", enrichedAt? }
```

No — `dictionaryEntry` is a **shared cache**, one row per unique term, with no relationship to any single user. The first time the server resolves "ephemeral" (dictionary API, then AI enrichment), it is saved here, and every later request for that term is answered from this table. No repeat API call, no repeat cost.

**Only the server may write this table.** `word.create` accepts a `definition` from the device, but stores it on that user's own `word.definitionOverride` — never here. This is the privacy rule the whole product rests on: readers share *how often a word was saved*, never *what it means*. If a client could write the shared row, the first person to capture a term would define it, permanently, for every other reader, with no way to correct it. `db:smoke` asserts this directly.

Because of that, `word.dictionaryEntryId` stays `null` until a server-side resolver fills it. Every device answers its own lookups from the bundled dictionary offline, or from the server's resolved entry when online.

`term` here holds the **normalized** form — a lowercased match key, not a display string. Anything joining to this table must normalize first; joining a display-cased `"Serendipity"` silently matches nothing.

AI enrichment (`exampleSentence`, `usageNote`, and `enrichedAt` marking when it last ran) lives on this shared row for the same reason the definition does: it's what holds the spec's cost target that *each unique word triggers at most one AI call across the entire user base*. Enrich once, serve forever. `dictionary.lookup` now writes all three — `enrichedAt` doubling as the claim that keeps concurrent lookups of a new word from buying two enrichments; see [AI enrichment](/docs/ai-enrichment). A per-word example sentence column used to exist alongside it and was removed — one shared row is the whole point, and the fallback chain it created was a branch in two screens for a case nobody had asked for.

`word.definitionOverride` is the other half of that rule. It holds anything the device supplied — the bundled dictionary's wording, or text the user typed themselves — and only that one user ever sees it. Display always reads `word.definitionOverride ?? word.dictionaryEntry?.definition`.

One deliberate simplification: `dictionaryEntry` stores exactly *one* definition per term, even though words often have multiple senses ("bank" the building vs. "bank" the riverside). This table represents "the best known resolution we have," not a full multi-sense dictionary — that's a different concern, handled entirely on-device (see [Offline dictionary](/docs/offline-dictionary)), because the on-device WordNet data is static reference data with no server-side equivalent, while this table's real analog is the on-device `dictionary` table's `cached` rows, which are *also* single-row-per-term. The two designs already agree; it isn't an oversight.

## Settings: `userPreference`

```ts
// schema/preference.ts (shape)
userPreference: { userId (PK), contributeToAggregateByDefault, offlineDictionaryTier: "core" | "extended" }
```

A 1:1 sidecar table for app settings, kept *separate* from `user` rather than adding columns directly to it — because `user` is generated and migrated by Better Auth, and mixing app-specific settings into a table a third-party library owns is asking for a migration conflict eventually.

`preference.get` and `preference.update` ([API layer](/docs/api-layer#the-preference-router)) are the way in. For a long time this table had a reader and no writer — `word.create` consulted `contributeToAggregateByDefault`, and nothing could change it, so the opt-out below was unreachable in practice.

The default values live in `@better-vocab/domain` as `PREFERENCE_DEFAULTS`, and are applied in two places from that one definition: as the Postgres column defaults, and as what `preference.get` returns for a user who has no row yet. Reading preferences therefore never creates a row.

A `pushToken` table used to sit here for the weekly digest. It was deleted: there is no push-sending code anywhere in the repo, and registering Expo tokens is a few minutes of work whenever the digest actually gets built. Same principle as `book.raw` above — schema with no producer is a liability, not a head start.

## How it all connects

```
user ──┬── folder ──── book
       │      │
       │      └── word ──┬── dictionaryEntry   (shared: many words point to one entry)
       │                 └── (denormalized userId + bookId, see above)
       └── userPreference (1:1)
```

## Worked example: logging a word

Walking through what `word.create` actually does when a user in the "Dune" folder adds the word "ornithopter" (see [API layer](/docs/api-layer) for the procedure itself):

1. Confirm the "Dune" folder belongs to this user, and grab its `bookId` while already fetching that row.
2. Normalize the term to `"ornithopter"`.
3. Check `dictionaryEntry` for an existing `"ornithopter"` row — **read only**. Someone else has likely already looked this word up, so link to that shared row if it exists. If it doesn't, any definition that came with the request is stored on *this user's* `definitionOverride` instead. Capture never writes the shared table; only `dictionary.lookup` does. A client that could write it would let the first person to capture a term define it permanently for every other reader.
4. Look up this user's `userPreference` to snapshot their current aggregate opt-in setting — falling back to `PREFERENCE_DEFAULTS` if they have never saved one.
5. Insert the `word` row — `userId`, `folderId`, `bookId` (all three, even though two are technically derivable), the term, the resolved `dictionaryEntryId` (or `null` if still pending), and the snapshotted preference. If this exact `(folderId, normalizedTerm)` already exists, the insert quietly no-ops and the existing row is returned instead.

The crowdsourced view for "Dune" later runs, roughly:

```sql
SELECT normalized_term, COUNT(DISTINCT user_id)
FROM word
WHERE book_id = 'dune-id' AND contributes_to_aggregate = true
GROUP BY normalized_term
ORDER BY count DESC;
```

— which is exactly the query the `bookId` denormalization and its index exist to make fast. There is deliberately **no** materialized `book_word_aggregate` counter table; one existed and was deleted. A counter counts *captures*, so one user with the word in ten folders would read as ten readers, and keeping it accurate means getting increment-on-create, decrement-on-delete, opt-out flips, and folder cascades right in four separate places. `COUNT(DISTINCT user_id)` is both smaller and more correct. Add a counter back only when this query shows up in slow logs.

It is also computed live rather than cached: a cached/stale version of this list risks showing outdated (and potentially spoiler-revealing) results if it's ever served while offline. That query is `word.suggestions` ([API layer](/docs/api-layer#wordsuggestions)), which adds two exclusions to the shape above — your own captures, and anything already in the folder you're looking at — and returns counts with no definition text at all.
