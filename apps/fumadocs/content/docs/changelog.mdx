Notable changes to the codebase, newest first. This tracks *decisions and their reasons*, not every commit — for the full list, read `git log`. Anything marked **Breaking** changes behaviour an existing caller depends on.

## Unreleased

### A bundled dictionary, and a downloadable pack

The offline dictionary is real. `core` — 74,441 terms, 9.2 MB — ships in the app binary and merges on first launch, so a reader who has never had signal still gets definitions. `extended` — 127,311 terms across 185,129 senses, 25 MB — downloads from Settings once `EXPO_PUBLIC_DICTIONARY_PACK_URL` points at a hosted file. See [Offline dictionary](/docs/offline-dictionary#getting-the-two-tiers-onto-a-device).

Both land through the same three statements. SQLite copies the rows itself; nothing is parsed in JS:

```sql
ATTACH DATABASE ? AS pack;
INSERT OR IGNORE INTO dictionary (...) SELECT ..., ?, rank FROM pack.dictionary;
DETACH DATABASE pack;
```

74,441 core rows in 86 ms; 184,356 extended rows in 272 ms.

<Callout type="warn">
The bundled core is **merged, not handed to `SQLiteProvider` as `assetSource`** — which was the documented plan and is a trap. The built asset carries only the `dictionary` table, but the build script stamps `PRAGMA user_version = 3` on it, so `migrateLocalDb` would return early and never create `pending_sync` or `app_setting`; the first theme save would throw on a fresh install. Merging costs one copy of the rows, keeps `local-db.ts` the only owner of the schema, and works on upgrade — where `assetSource` does nothing, because the database already exists.
</Callout>

The pack is hosted as a **plain static file**, deliberately not served by `apps/server`: tRPC is the wrong transport for a 25 MB binary, and a static host keeps the download alive when the API is down.

### The WordNet pipeline, fixed and pinned

`wordnet-to-dictionary.ts` had never been run end to end. It produced **963 words**. Three bugs, none of which errored:

- It built lemmas from `src/sense-orders.csv`, which is not the lemma index — it's ~1,300 rows of manual sense-order *corrections*. The vocabulary is in `entries-*.json`. That alone was 963 → 75,113.
- Sense rank restarted at 0 per part of speech, but the device index is unique on `(term, source, rank)` — so "run" as a verb would have collided with "run" as a noun and `INSERT OR IGNORE` would have dropped senses silently.
- WordNet examples aren't always strings; attributed quotations are `{ source, text }` objects, and 589 of them reached the SQLite driver as unbindable values.

The source also moved from `src/yaml/*` on `main` to the **JSON export attached to a tagged release**: 72 requests became one 9.5 MB zip, minutes became two seconds, and the build is reproducible. `main` had already drifted past the 2025 release — 107,528 synsets against 107,519 — which is enough for two builds of "the dictionary" to be quietly different artifacts. Dropped the `yaml` dependency; `unzip` is now a build-time requirement.

### The review run, the word screen, and settings

Three more screens off the design canvas, all on procedures that already existed and had no caller.

**`review`** renders `word.quiz`: a progress rail, the blanked sentence, and a reveal carrying the definition and usage note. The run is fetched once and never refetched mid-session — stamping a review would reorder the deck under the reader. The design's three grades collapse to two, because `word.update` records a review as a timestamp and not a grade; "Almost" and "Got it" would write the identical row.

**`word/[id]`** is the first screen to render `dictionary_entry.exampleSentence` and `usageNote`. It reads its row from the folder list's cache rather than adding a `word.byId` — the previous screen just fetched it.

**`settings`** is the first caller of `preference.get`/`update`, and hosts the dictionary download. Sign-out moved into it from its own tab-header button; the header slot is now a gear.

`shelf`, `folder/[id]` and `search` were restyled to the canvas at the same time. `folder.list` gained a `wordCount` — one grouped query, which let the home page drop a `listByFolder` call it was making purely to count.


### A welcome screen and a home page, from the design canvas

Two screens built from the Claude Design project, in the app's own colour scheme rather than the design system's: the canvas is cyan-and-magenta on a Broadsheet system, and this app is Ochre spot, so what came across is layout, hierarchy and copy.

**Welcome** (`app/(auth)/index.tsx`) is the group's index, so a signed-out reader lands there rather than on a bare form. Both buttons lead to `sign-in`, which already renders sign-in and sign-up together — two buttons because the design asks a returning reader a different question, one destination because there is only one. No "seen once" flag: signed-out is the condition it renders on.

**Home** (`app/(tabs)/index.tsx`) is a new landing tab. The shelf **moved to `/shelf`** with its own tab rather than being replaced — it owns folder creation and Hardcover search, and the design treats home and shelf as different screens anyway. Home shows a greeting and due count, "currently reading" from the newest `reading` folder with its book and saved-word count, a three-up capture row, and the first three due words with the mastery dot the scheme reserves for exactly that.

`word.quiz` cards gained a `state` (`new` until first review, `learning` after) to feed those dots.

<Callout type="warn">
Four designed elements are deliberately not implemented, because nothing stands behind them. **Scan page** and **Say it** render disabled — OCR is out of scope for V1 (SoftwareSpec §11) and voice needs an STT library nobody has picked. **Start review** is omitted rather than disabled, since `word.quiz` already serves it and only the screen is missing. **Reading progress** and the **streak line** are dropped outright: there is no progress or streak in the data model, and a landing screen that invents numbers is worse than a quieter one. The onboarding copy also lost its "point your camera at a page" promise for the same reason.
</Callout>

The canvas's headline is a CMYK print treatment — three misregistered plates built from `mix-blend-mode`, SVG `feColorMatrix` filters and a pointer-driven registration animation. None of that exists in React Native, and its inks are the colours this app doesn't use, so the headline is set plainly in the reading face.

### Usage contexts, and a quiz built out of them

Enrichment now returns three usage sentences per term instead of one, each with the word **brace-marked** — `"The house had an {eldritch} stillness about it."` — and `word.quiz` turns them into fill-in-the-blank cards over the reader's own words ([API layer](/docs/api-layer#wordquiz)).

The marking is the whole design. One stored string becomes both a context panel entry (braces stripped) and a cloze card (span replaced by a blank, its contents kept as the answer), so neither reader has to find the word in the sentence. Searching for the term at read time would blank the wrong span or none at all — a context for "run" may say "running" — and a card whose prompt contains its own answer is worse than no card. `parseContext` in `@better-vocab/domain` is the one definition of that format, read by the quiz builder, the app's panel, and enrichment's own validation.

The quiz **costs no AI call of its own**: contexts live on the shared, term-keyed row, so every card was generated by the one enrichment call that term will ever get, however many readers quiz on it. `exampleSentence` is no longer generated separately either — it's the first context with its braces removed, so there's one artifact to get right instead of two that can disagree.

A word is excluded for one of three reasons, each a rule rather than an accident: it's `mastered` (which is what mastering is *for*), it has no resolved entry (captured offline, never looked up — no sentence to blank), or its entry carries no contexts.

<Callout type="info">
The card sort ends on `word.id`. Words written in one statement — an offline flush, or the seed — share `createdAt` to the microsecond, and without a total order Postgres may return them differently between calls; a quiz that reshuffles on every open reads as a bug in the session rather than a missing sort key. `db:smoke` caught that on its second run, which is the case a single-run test would have missed.
</Callout>

Migration `0003_add_dictionary_contexts`. `db:smoke` is at 38 checks.

### The Ochre spot scheme, as the default page theme

The app opens on **Ochre spot**: a single-accent scheme where ochre is spent only on the reader's own saved words and the one main action per screen, and everything else is ink, paper, or grey. Other readers' data stays muted by rule — crowdsourced counts are reference material, not the reader's progress. See [Theming](/docs/theming).

`ochre` is the default page, and the scheme's night half replaces Kindle's true-black `dark`: both are "the dark theme", and keeping a `#000` page with an unrelated blue accent would have left one theme outside the new system. Kindle's Sepia and Green stay untouched — page colours are a different axis from an accent scheme.

An earlier draft of this entry described daisyUI's `autumn` palette in this slot. That scheme was replaced before release, and the daisyUI dependency came out with it rather than being left installed with no consumer.

The scheme arrived as a NativeWind v4 drop — a `tailwind.config.js`, `@tailwind base;` directives, colours as space-separated RGB channels for `<alpha-value>`. None of that applies to this app, which runs Uniwind with Tailwind v4: CSS-first, no JS config, and alpha handled by v4 itself. What ported is the palette and its rules.

Its own vocabulary — `primary-pressed`, `primary-tint`, the three mastery states — is registered as Tailwind colours, so `bg-primary`, `text-ink/70` and `text-state-learning` compile to real RN styles. The tokens that *have* a HeroUI counterpart are declared as aliases (`--color-ink: var(--foreground)`) rather than copies, so they follow the page the reader chose instead of freezing at one theme's value — verified in the bundle, where `--color-ink` compiles to a function reading `--foreground` rather than a literal.

**A `DEFAULT_THEME` constant does not make a theme the default.** Uniwind starts on `light` with no config option to change it, and `light` is a theme a reader can legitimately pick — so "current theme is light" and "reader hasn't chosen" are indistinguishable at read time, which made the existing read-side fallback dead code. The absence of a *stored* value now selects the default, applied in the load effect behind the `isThemeReady` gate that already holds the splash.

`The reading face moves to **Source Serif 4**, which is what the scheme asks for — five faces (regular, italic, medium, semibold, bold), with `font-body` / `font-heading` / `font-italic` aliased onto them so the face is one edit rather than five. Literata, which stood in for Bookerly while the Kindle pages were the whole design, came out with it. React Native registers each face as its own family, so italic is `font-italic` rather than the `italic` utility.

`lib/palette.ts` serves the places a className can't reach (StatusBar, SVG fills, `Animated`), re-exporting the scheme's values so ochre has one spelling. Its `usePalette()` reads the app's theme context rather than RN's `useColorScheme()`: the theme here is a persisted choice across five pages, not a mirror of the OS setting.

<Callout type="info">
Adding a theme touches three files in step — the `@variant` block, `extraThemes` in `metro.config.js`, and `READING_THEMES` in the theme context — and then needs a Metro restart, because the theme union in `uniwind-types.d.ts` is generated from `extraThemes` and gitignored. A stale one is what makes `Uniwind.setTheme("autumn")` fail to typecheck.
</Callout>

### The rest of the server: AI enrichment, notes, reviews, renames, account deletion

Every column and every flow section that had a server-side half missing now has one. What's left in [Implementation status](/docs/implementation-status) is screens, an asset, and two library choices.

**AI enrichment, once per word, for everyone** ([new docs page](/docs/ai-enrichment)). `dictionary.lookup` now finishes by adding an example sentence and a usage note to the shared `dictionaryEntry` row. `exampleSentence`, `usageNote` and `enrichedAt` had been schema with no producer since the first migration.

`enrichedAt` is both the marker and the lock: the claim is a conditional update (`SET enriched_at = now() WHERE enriched_at IS NULL`) taken *before* the call, so two readers hitting the same brand-new word buy one enrichment between them rather than one each. That is what makes the spec's cost target — each unique word triggers at most one AI call across the entire user base — true under concurrency rather than only on paper. A failed call releases the claim, so a timeout costs the term nothing worse than staying plain until its next lookup.

The provider sits behind one function, `enrichDefinition` (`packages/api/src/enrich.ts`), calling the model through [Vercel AI Gateway](/docs/ai-enrichment#swapping-the-model) with `generateObject` and a Zod schema. The model is one `provider/model` string (`zai/glm-4.7-flashx`, ~$0.06/$0.40 per million tokens), so changing model *or vendor* is that line — no second SDK, account, or key, and never the tRPC contract. A small/fast tier on purpose: an example sentence is not frontier-reasoning work, and this runs once per unique word for the whole user base. Cheap models have quirks — this one returns the right fields nested under a key it invented on about half of calls — so the call carries a `repairText` unwrap, asserted in `db:smoke` against captured payloads. `AI_GATEWAY_API_KEY` is server-only (the Expo app never talks to a provider) and **optional** — without it, lookups resolve and cache base definitions exactly as before, they simply never gain a sentence. Every failure mode returns the base row, because enrichment is only ever an upgrade on a definition the reader already has; it must not be able to turn a working lookup into a broken screen.

The prompt requires a neutral invented sentence and forbids referencing a plot, character, or setting. A sentence borrowed from the book a reader is halfway through is a spoiler.

**Three columns got their writers.** `word.personalNote` (an annotation *alongside* the definition, not replacing it) and `word.lastReviewedAt` (stamped by `word.update({ reviewed: true })`, so a flashcard turn has somewhere to sync) were both schema-only. Each field of `word.update` is written only when sent, so a review turn cannot blank a note typed on the same row, and the timestamps are the server's — a device with a wrong clock cannot backdate a review.

**Account deletion.** `deleteUser` is enabled in Better Auth, gated on the caller's password or a session fresher than a day. Every domain table references `user.id` with `ON DELETE CASCADE`, so the row takes the folders, words and preferences with it — and those captures leave the crowdsourced counts too, which is the right reading of "delete my data". Changing an *email* stays unbuilt for a concrete reason: Better Auth requires a verification mail, and this app has no email sender.

<Callout type="warn">
**Breaking:** `folder.updateStatus` is now `folder.update`, taking an optional `title` alongside the optional `status`. The status chips call it exactly as before; the rename is the new half. A folder's `title` is its own label, denormalized from `book.title` at creation and free to diverge after — renaming never touches the shared `book` row other readers of that book join to. There is still no way to change a folder's `bookId`, for the reason recorded in the [data model](/docs/data-model): `word.bookId` is snapshotted at capture time.
</Callout>

**Removed: `privateData`.** A scaffold procedure that returned the session user to prove auth worked. `db:smoke` proves it now, from both sides of the ownership boundary.

### Shared domain package, one definition resolver, one ownership rule

An architecture review turned up the same logic written in several places, each copy free to drift from the others. All of it now has a single home.

**`@better-vocab/domain` — a new dependency-free package.** It exists because `apps/native` cannot import `packages/db`: that would pull Postgres drivers into the React Native bundle. Anything the server and the app must agree on lives here instead of being retyped on both sides. `packages/db` builds its `pgEnum`s from these arrays, `packages/api` builds its `z.enum`s from them, and the Expo app reads them directly.

- **`normalizeTerm`** — the match key. Every join between a captured word and a definition matches on this: the shared `dictionary_entry` table, the on-device `dictionary` table, and the crowdsourced aggregate's `GROUP BY`. It had been written out as `term.trim().toLowerCase()` at four call sites across three packages, with the rule itself recorded only in a schema comment.

  One of those four was `scripts/build-dictionary-db.ts`, which stamps the bundled dictionary at build time. Had it ever normalized differently from the runtime lookups, every offline lookup would have missed — with no error, no crash, and nothing in the repo that would have caught it. That is the reason this is a module rather than a convention.

- **Closed value sets** — `FOLDER_STATUSES`, `CAPTURE_METHODS`, `DICTIONARY_TIERS`, `OFFLINE_DICTIONARY_TIERS`, `DICTIONARY_SOURCES`. `folder_status` alone had been declared three times: a `pgEnum`, a `z.enum`, and an `as const` array in the app.

- **`PREFERENCE_DEFAULTS`** — applied by `packages/db` as the column defaults *and* returned by `preference.get` for a user with no row, so "the default" is one value rather than one per reader of it.

`dictionary_source` and `DICTIONARY_TIERS` were deliberately **not** merged, despite `bundled` and `core` looking like duplicates. They sit on different axes: one is the provenance of a shared server row, the other is which on-device tier holds a copy. The same row can be `bundled` provenance and `cached` tier on the same phone.

**One definition resolver.** `useDefinition` (`apps/native/hooks/use-definition.ts`) is now the only answer to "get me a definition for this term" — device tiers first, `dictionary.lookup` second, result written back to the `cached` tier. Three separate decisions used to answer that question: the SQL that ranked the on-device tiers, the Add Word screen that chose between device and server, and the server procedure that chose between its cache and Datamuse.

It returns a `found` / `missing` / `unreachable` union, so a screen renders a state instead of merging two query results by hand. `apps/native/lib/dictionary.ts` owns the reads and writes; screens no longer touch SQL.

**Fixed: nothing wrote the `cached` tier.** The lookup query ranked `cached` highest, but no code ever inserted a row with that source — an online result was displayed and thrown away. `cacheDefinition` now writes it back, so the second lookup of a word works on a plane. The tier's top priority had been unreachable since it was introduced.

**One ownership rule.** `ownedBy` + `assertOwned` (`packages/api/src/ownership.ts`) replace six hand-written `(id, userId)` predicates in three shapes.

<Callout type="warn">
**Breaking:** `word.delete` and `folder.delete` used to return `{ id }` whether or not a row matched, so deleting a word that belonged to someone else — or one already deleted — reported success. Both now throw `NOT_FOUND`, matching what `update` always did. Deleting the same row twice is no longer a silent no-op.
</Callout>

Both failures are `NOT_FOUND` rather than `FORBIDDEN`, deliberately: a caller has no business learning that a row exists but belongs to someone else.

**One Postgres connection pool.** `createAuth()` called `createDb()` a second time, so every server process held two pools that shared nothing — one for tRPC, one for Better Auth's adapter. It now takes the connection as a parameter, which also makes the adapter injectable for tests.

### `preference` router

`user_preference` had a schema and a reader but no writer: `word.create` consulted `contributeToAggregateByDefault` to decide whether a capture joins the crowdsourced aggregate, and nothing let a reader change it. The opt-out the [privacy model](/docs/data-model) promises existed only as a column.

- `preference.get` — never writes. A user with no row gets `PREFERENCE_DEFAULTS`, so a settings screen can open without a write on first launch.
- `preference.update` — upserts field by field, so a toggle sends only what it changed rather than echoing back the rest of the screen. `updatedAt` is always in the `SET` clause, which keeps the timestamp honest on the conflict path (`$onUpdate` only fires for a plain `UPDATE`) and means the clause is never empty.

No settings screen calls these yet.

### `word.createMany` — the offline flush endpoint

`pending_sync` has been in the on-device schema since the first migration with nothing on either end of it. The server half now exists.

`createMany` takes up to 100 queued captures and returns a result **per capture**, not one verdict for the batch:

| Status | Meaning | What the device does |
| --- | --- | --- |
| `saved` | Written, or already present | Delete the queued row |
| `dropped` | Permanently un-writable — e.g. the folder was deleted on another device | Delete it too; retrying will never succeed |
| *(thrown error)* | Transient — lost connection, database fault | Keep the queue, try again later |

Partial success is the point: a folder deleted on another device must not strand every other queued word behind it. Ownership is resolved per folder and the preference read once, both outside the loop.

`create` and `createMany` share one private `captureWord`, so the rule that a client never writes `dictionary_entry` cannot hold for the live save and quietly lapse for the flush.

The device half still does not exist — nothing writes a `pending_sync` row when a capture happens offline, and nothing calls `createMany` on reconnect.

### Checks

`db:smoke` grew from 19 assertions to 28. The new ones cover `normalizeTerm` directly, the delete-ownership fix, the preference round trip (including that the opt-out actually reaches a capture rather than merely persisting), and the flush — including that resending a queue after a crash is idempotent.

One new check reads the live `pg_enum` labels back out of Postgres and compares them to the domain arrays. Asserting the `pgEnum`s match the arrays would prove nothing, since they are built from them; asking the database catches the case that actually bites, which is a value added without a generated migration.

## 2026-09-07 — Book search and dictionary lookup

`book.search` proxies [Hardcover](/docs/book-search)'s GraphQL API so the token never leaves the server, and folder creation links the picked result. `dictionary.lookup` resolves definitions through Datamuse and caches them in `dictionary_entry` ([API layer](/docs/api-layer#the-dictionary-router)).

Schema with no producer was deleted rather than kept warm: `book_word_aggregate`, `push_token`, `book.raw`, `book.topics`, `dictionary_entry.audio_url`, `word.example_sentence`, and the FTS5 index in the dictionary build. The bet is that adding a column alongside the feature that reads it is cheaper than maintaining schema for a feature that may never arrive.

## 2026-09-03 — First vertical slice

Shelf, folder detail, and word capture, walkable end to end: sign in, see your shelf, create a folder, log a word into it, browse and search. Kindle-style reading themes and a serif reading font landed alongside it.
