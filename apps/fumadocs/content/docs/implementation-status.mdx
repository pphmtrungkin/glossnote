Tracked against the GlossNote user-flow doc, section by section. "Schema only" means the Postgres or on-device tables exist, but no procedure or UI actually uses them yet — a foundation, not a feature.

| Flow section | Status |
| --- | --- |
| Onboarding | Partial — email/password auth works ([Authentication](/docs/authentication)); magic link and OAuth aren't configured. The dictionary bundling pipeline exists but hasn't been run for real, so first-launch download isn't wired up. No onboarding UI. |
| Creating a folder | `folder.create` / `list` / `updateStatus` / `delete` implemented ([API layer](/docs/api-layer)) and wired to the Shelf tab — list, create, status chips, long-press delete. `book.search` proxies Hardcover and the Shelf's new-folder form searches it, links the picked book, and falls back to a typed title ([Book search](/docs/book-search)). Untested against the live API — set `HARDCOVER_API_TOKEN` and run a real search. |
| Logging a word — offline | The single-table `dictionary` lookup exists ([Offline dictionary](/docs/offline-dictionary)) and the add-word screen queries it as you type — but no `.db` asset ships yet, so the table is empty at runtime and lookups fall through. `pending_sync` exists and nothing writes to or flushes it, so the capture screen still requires the network to save. |
| Logging a word — online | `word.create` implemented and wired to the add-word modal — accepts a definition from the offline dictionary or typed by hand, or leaves the word "pending" ([Data model](/docs/data-model)). No dictionary-API/AI-definition resolver, no text-to-speech, and voice entry needs an on-device speech-to-text library that hasn't been chosen. |
| Browsing inventory | `word.listByFolder` and `word.search` implemented, behind the folder detail screen and the Search tab. Per-word `mastered` toggle and delete are wired up; no sorting or filtering beyond the term match yet. |
| Crowdsourced discovery | Not implemented as a procedure — but the query is now verified. `book.search` means `book` rows finally exist, so `word.bookId` has something to group by, and `db:smoke` asserts the live aggregate ranks by distinct readers, honours opt-out, and joins definitions on the normalized term. Deliberately not cached and deliberately not a counter table ([worked example](/docs/data-model#worked-example-logging-a-word)). |
| Review / retention | `word.update` supports toggling `mastered`, stamping and clearing `masteredAt` with it. No review-session UI, no weekly digest job, and no push infrastructure at all — the unused `pushToken` table was deleted rather than left as scaffolding. |
| Settings / account | `userPreference` schema exists and is read by `word.create`. No settings screen, no account-deletion config, no export, no "Sync now" button. |
| Mode indicators | Not implemented — `expo-network` is installed but nothing uses it yet. |

## What this means in practice

The data model — both Postgres and the on-device SQLite schema — was designed section-by-section against the full flow doc, so almost everything above has a home to land in already. The first vertical slice is now walkable end to end: sign in, see your shelf, create a folder, log a word into it, browse and search. Book search closed the biggest gap: `book` rows now have a producer, which is what the crowdsourced aggregate was waiting on. What's still missing is the sync-flush job, the aggregate procedure and its tab, an AI enrichment client, and the screens that depend on them (onboarding, review sessions, settings). Two items additionally need a library decision before they can be built at all: on-device speech-to-text (voice capture) and a push-notification sending mechanism (weekly digest).

One change of direction worth recording: several tables and columns that existed as groundwork — `book_word_aggregate`, `push_token`, `book.raw`, `book.topics`, `dictionary_entry.audio_url`, `word.example_sentence`, and the FTS5 index in the dictionary build — were **deleted** rather than kept. None had a producer or a consumer, and each carried real maintenance cost. The bet is that adding a column alongside the feature that reads it is cheaper than keeping schema warm for a feature that may never arrive.

## Checking it still works

`bun run db:smoke` is the repo's only automated check — a self-cleaning script that drives the real `appRouter` against a seeded local Postgres and asserts what the schema, not TypeScript, enforces: relation joins, ownership scoping, the partial unique index on `(user_id, book_id)`, capture idempotency, cascade deletes, the Hardcover book upsert, and the live aggregate query. Run `bun run db:start && bun run db:seed` first. It never calls Hardcover.
