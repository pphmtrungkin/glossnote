Tracked against the GlossNote user-flow doc, section by section. "Schema only" means the Postgres or on-device tables exist, but no procedure or UI actually uses them yet — a foundation, not a feature.

| Flow section | Status |

The dictionary pipeline has now been run for real: a 9.2 MB `core` asset ships in the binary and merges on first launch, so offline lookups work before the app has touched the network ([Offline dictionary](/docs/offline-dictionary#getting-the-two-tiers-onto-a-device)). A welcome screen now opens the signed-out flow (`app/(auth)/index.tsx`), built from the design canvas; both its buttons lead to the combined sign-in/sign-up screen, since that screen already carries both forms. |

Untested against the live API — set `HARDCOVER_API_TOKEN` and run a real search. |
| Logging a word — offline | `useDefinition` resolves a term against the device first and the server second, caching the answer locally for next time ([Offline dictionary](/docs/offline-dictionary#one-resolver)). The bundled `core` tier now ships — 74,441 terms, merged on first launch — so common words never reach the network, and the downloadable `extended` pack (127,311 terms) installs from Settings once `EXPO_PUBLIC_DICTIONARY_PACK_URL` points at a hosted file. `word.createMany` is the flush endpoint the queue was designed for and is tested, but nothing on the device writes a `pending_sync` row or calls it, so the capture screen still requires the network to save. |

AI enrichment now runs on top of that: `dictionary.lookup` adds an example sentence and usage note to the shared row, once per unique term across the whole user base, behind `enrichDefinition` ([AI enrichment](/docs/ai-enrichment)) — optional, so the app still resolves definitions without a key. One live call verified end to end; the write-back path through `dictionary.lookup` still hasn't run against a live model, so look up a word nobody has resolved yet and read the row back. No screen renders `exampleSentence`/`usageNote` yet. No text-to-speech, and voice entry needs an on-device speech-to-text library that hasn't been chosen. |

The shelf moved to its own tab rather than being replaced. Three designed affordances are deliberately absent or inert — see below. |
| Browsing inventory | `word.listByFolder` and `word.search` implemented, behind the folder detail screen and the Search tab. A word row now opens `word/[id]`, the design's word screen, which is where `mastered`, the personal note, and the AI `exampleSentence`/`usageNote` are rendered — the first reader those two columns have had. Delete is a long-press. No sorting or filtering beyond the term match yet. |
| Crowdsourced discovery | Implemented. `word.suggestions` returns terms other readers of the book saved, minus your own and minus what's already in your folder, ranked by distinct readers ([API layer](/docs/api-layer)). The folder screen shows them, resolving each definition from the *local* dictionary — counts are shared, definitions are not. Deliberately not cached and deliberately not a counter table. |
| Review / retention | `word.quiz` builds fill-in-the-blank cards from the shared usage contexts on `dictionary_entry`, scoped to a folder or run across all of them, least-recently-reviewed first ([API layer](/docs/api-layer#wordquiz)) — the flashcard session the flow asks for, costing no AI call of its own. `app/review.tsx` renders it: a progress rail, the blanked sentence, a reveal carrying the definition and usage note, and "Not yet" / "Got it". The run is fetched once and never refetched mid-session, since stamping a review would reorder the deck under the reader. Home and the folder screen both open it. `word.update` toggles `mastered` (stamping and clearing `masteredAt` with it) and takes `reviewed: true` to stamp `lastReviewedAt`, so a flashcard turn has somewhere to sync to. The design's three grades collapse to two, because `word.update` records a review as a timestamp and not a grade — two buttons writing the identical row is a distinction the data can't keep. The weekly digest is still absent and stays that way until there is push infrastructure to deliver it — the unused `pushToken` table was deleted rather than left as scaffolding, and a digest query with no consumer would be the same mistake. |
| Settings / account | `preference.get` / `preference.update` implemented ([API layer](/docs/api-layer#the-preference-router)), so the crowdsourced opt-out and the offline dictionary tier are both settable. `app/settings.tsx` is the caller — grouped rows from the design canvas, covering the offline dictionary download, the aggregate opt-out, and sign-out, which used to be a tab-header button of its own. Account deletion is now enabled in Better Auth (password, or a session fresher than a day; every domain table cascades off `user.id`). Changing an email still isn't possible — Better Auth requires a verification mail and this app has no email sender. Export is deliberately client-side (the flow calls for a local file generated from cached data), and "Sync now" waits on the device queue. |
| Mode indicators | Not implemented — `expo-network` is installed but nothing uses it yet. |

## What this means in practice

The data model — both Postgres and the on-device SQLite schema — was designed section-by-section against the full flow doc, so almost everything above has a home to land in already. The first vertical slice is now walkable end to end: sign in, see your shelf, create a folder, log a word into it, browse and search. Book search closed the biggest gap: `book` rows now have a producer, which is what crowdsourced discovery was waiting on — and that feature now exists end to end. The bundled dictionary asset and the screens that were waiting on the server surface — review, settings, word detail — now exist. What's still missing on the client is the offline capture queue and the screens with no server behind them at all. AI enrichment closed on the server side: every column in `dictionary_entry` now has a producer. Offline sync is now half-built rather than absent: the server endpoint exists and is tested, the device-side queue and flush trigger are not written. Two items additionally need a library decision before they can be built at all: on-device speech-to-text (voice capture) and a push-notification sending mechanism (weekly digest).

The table now reads as a client-side backlog rather than a server one: every flow section above has the procedures it needs, and what remains for each is a screen, an asset, or a library choice.

One change of direction worth recording: several tables and columns that existed as groundwork — `book_word_aggregate`, `push_token`, `book.raw`, `book.topics`, `dictionary_entry.audio_url`, `word.example_sentence`, and the FTS5 index in the dictionary build — were **deleted** rather than kept. None had a producer or a consumer, and each carried real maintenance cost. The bet is that adding a column alongside the feature that reads it is cheaper than keeping schema warm for a feature that may never arrive.

## Checking it still works

`bun run db:smoke` is the repo's only automated check — a self-cleaning script that drives the real `appRouter` against a seeded local Postgres and asserts what the schema, not TypeScript, enforces: relation joins, ownership scoping, the partial unique index on `(user_id, book_id)`, capture idempotency, cascade deletes, the Hardcover book upsert, the enrichment claim on `dictionary_entry`, and the live aggregate query. Run `bun run db:start && bun run db:seed` first. It calls neither Hardcover nor an AI provider — the enrichment checks assert the *unconfigured* path, which is also the failure path, and skip themselves when `AI_GATEWAY_API_KEY` is set rather than spending money on a smoke run.
