This page tracks the GlossNote user-flow document, section by section.

Two words are used in a specific way:

- **Built** — a procedure and a screen both exist, and you can use the feature.
- **Schema only** — the Postgres or on-device tables exist, but no procedure or screen uses them yet. That is a foundation, not a feature.

## Onboarding

Email and password sign-in works ([Authentication](/docs/authentication)). Magic link and OAuth are not configured.

The dictionary pipeline has been run for real. A 9.2 MB `core` asset ships inside the app binary and merges on first launch, so offline lookups work before the app has ever used the network. See [Offline dictionary](/docs/offline-dictionary#getting-the-two-tiers-onto-a-device).

The signed-out flow has three screens, all built from the design canvas:

| Route | Screen |
| --- | --- |
| `app/(auth)/index.tsx` | Welcome |
| `app/(auth)/sign-in.tsx` | Sign in |
| `app/(auth)/sign-up.tsx` | Create account |

Sign in and sign up replace each other with `router.replace`, so the back stack never grows a chain of them.

The two forms (`components/sign-in.tsx`, `components/sign-up.tsx`) are plain React Native inputs, not HeroUI form components. They share one labelled-field component, `components/text-field.tsx`, which owns the focus ring, the error message, and the show/hide toggle on the password field.

## Creating a folder

`folder.create`, `list`, `update` and `delete` are implemented ([API layer](/docs/api-layer)) and wired to the Library tab: list, create, status chips, and a long-press sheet to make a shelf private or public, or to delete it.

`folder.update` can also rename a folder. No screen calls that half yet.

`book.search` proxies Hardcover. The Shelf's new-folder form searches it, links the picked book, and falls back to a typed title ([Book search](/docs/book-search)).

Still untested against the live API. Set `HARDCOVER_API_TOKEN` and run a real search.

## Logging a word — offline

`useDefinition` asks the server whenever the device is online, and the device's own dictionary when it is not, when the server fails, or when the server has no entry. Server answers are cached locally for next time ([Offline dictionary](/docs/offline-dictionary#one-resolver)).

Both dictionary tiers work:

- `core` (74,441 terms) ships in the binary and merges on first launch, so common words never reach the network.
- `extended` (127,311 terms) installs from Settings, once `EXPO_PUBLIC_DICTIONARY_PACK_URL` points at a hosted file.

The offline capture queue is now complete on both sides:

| Side | Where |
| --- | --- |
| Server | `word.createMany`, which reports each capture separately ([API layer](/docs/api-layer#wordcreatemany--sending-the-offline-queue)) |
| Device: write and send the queue | `apps/native/lib/pending-sync.ts` |
| Device: the one save path | `apps/native/hooks/use-capture-word.ts` |
| Device: flush on reconnect | `apps/native/hooks/use-pending-sync.ts` |

So saving a word with no signal now works. The word goes into `pending_sync`, the screen says it will sync later, and the flush runs when `expo-network` reports a connection again.

## Logging a word — online

`word.create` is implemented and wired to the add-word modal. A definition sent by the device is stored on that user's own row, never in the shared cache ([Data model](/docs/data-model)).

`dictionary.lookup` checks a new term against Datamuse, then has AI write its definition, example contexts and usage note in one call. The Datamuse check keeps words invented for a book from being defined, and Datamuse's own definition is saved instead when the AI call fails. Results are cached in `dictionaryEntry` for every reader. The add-word screen calls it whenever the device is online ([API layer](/docs/api-layer#the-dictionary-router)).

A row that came from Datamuse is enriched once afterwards, behind `enrichDefinition` ([AI enrichment](/docs/ai-enrichment)). AI is optional, so the app still resolves definitions with no API key.

The whole path through `dictionary.lookup` has run against the live gateway and a local database. Real words were saved already enriched, invented words returned `null` with no row, repeat lookups cost no AI call, and two lookups of one new word at the same moment bought one call ([AI enrichment](/docs/ai-enrichment#what-is-tested-and-what-is-not)).

Both AI columns now have readers: `app/word/[id].tsx` shows them, and the review card's reveal carries `usageNote`.

Not built: text-to-speech, and voice entry. Voice entry needs an on-device speech-to-text library, and none has been chosen.

## Home

Built from the design canvas (`app/(tabs)/index.tsx`):

- a greeting and a due count
- "currently reading", taken from the newest `reading` folder, with its book and saved-word count
- a three-button capture row
- the first three due words, each with its mastery dot

The shelf moved to its own tab instead of replacing this screen.

Three affordances from the design are deliberately absent or disabled — see [What we left out](#what-we-left-out).

## Browsing inventory

`word.listByFolder` and `word.search` are implemented, behind the folder detail screen and the Search screen, which Library's magnifier opens.

Tapping a word row opens `word/[id]`, the design's word screen. That screen renders `mastered`, the personal note, and the AI `exampleSentence` and `usageNote`.

Delete is a long-press. There is no sorting or filtering yet, beyond matching the term.

## Crowdsourced discovery

Built.

`word.suggestions` returns terms other readers of the book saved, minus your own words and minus anything already in your folder, ranked by the number of distinct readers ([API layer](/docs/api-layer)).

The add-word form shows them, and it is the only place the app recommends words. With the Word field empty it lists the most-saved five; after two typed letters it completes from them. Tapping one fills the field, and the definition resolves like a typed word's. Counts are shared; definitions are not.

The same form also shows AI-picked words for the book, grouped by subject, from `word.topicWords` ([API layer](/docs/api-layer#wordtopicwords)). The book's own page recommends nothing.

It is deliberately not cached, and deliberately not a counter table.

## Review / retention

`word.quiz` builds fill-in-the-blank cards from the shared usage contexts on `dictionary_entry`. A run can be scoped to one folder or cover all of them, least-recently-reviewed first ([API layer](/docs/api-layer#wordquiz)). It costs no AI call of its own.

`app/review.tsx` renders it: a progress rail, the sentence with a blank, a reveal with the definition and usage note, and two buttons — "Not yet" and "Got it".

The run is fetched once and never refetched during the session. Stamping a review would reorder the deck while the reader is using it.

Home, the folder screen and the Practise tab all open it. The Practise tab (`app/(tabs)/practise.tsx`) also lists every mastered word, from `word.mastered`.

`word.update` toggles `mastered` (setting and clearing `masteredAt` with it) and takes `reviewed: true` to stamp `lastReviewedAt`.

The design's three grades became two buttons, because `word.update` records a review as a timestamp, not a grade. Two buttons writing exactly the same row is a difference the data cannot keep.

The weekly digest is not built, and stays that way until there is push infrastructure to deliver it. The unused `pushToken` table was deleted rather than kept as scaffolding.

## Settings / account

`preference.get` and `preference.update` are implemented ([API layer](/docs/api-layer#the-preference-router)), so the crowdsourced opt-out and the offline dictionary tier can both be changed.

`app/(tabs)/you.tsx` is the caller. It has grouped rows from the design canvas, covering the offline dictionary download, the aggregate opt-out, and sign-out.

Account deletion is enabled in Better Auth (password, or a session fresher than one day; every domain table cascades off `user.id`). But no screen calls it yet.

Changing an email is still not possible. Better Auth requires a verification mail, and this app has no email sender.

Export is deliberately client-side: the flow asks for a local file built from cached data. "Sync now" is not built; the automatic flush covers the same job.

## Mode indicators

There is no offline banner in the UI yet.

`expo-network` is now used, though. `use-pending-sync.ts` watches connectivity to decide when to flush the queue, so the signal a banner would need is already in the app.

## Hardening

Both external proxies carry a per-user request budget, because they spend someone else's quota: 20 per minute for `book.search`, 60 per minute for `dictionary.lookup` ([API layer](/docs/api-layer#both-proxies-have-a-request-budget)).

Better Auth's rate limiter is enabled explicitly, not left to its `NODE_ENV` default, plus a custom rule for `/delete-user` ([Authentication](/docs/authentication#rate-limiting)).

Both use in-memory counters. That is correct for one server instance, and marked with a `ponytail:` comment for the day there are several.

## What this means in practice

The data model — Postgres and the on-device SQLite schema — was designed section by section against the full flow document. So almost everything above already had a place to land.

The first vertical slice now works end to end: sign in, see your shelf, create a folder, save a word into it, browse and search, review it.

The things that closed the biggest gaps, in order:

1. **Book search** gave `book` rows a producer, which is what crowdsourced discovery was waiting for.
2. **The bundled dictionary asset** made offline lookups real instead of theoretical.
3. **AI enrichment** gave every column in `dictionary_entry` a producer.
4. **The device queue** made `word.createMany` reachable, so offline capture round-trips.

Two items still need a library decision before they can be built at all:

- on-device speech-to-text, for voice capture
- a way to send push notifications, for the weekly digest

## Before the app can be public

One thing is **owed and not written**: a [DMCA takedown policy](/docs/dmca).

The app serves book covers uploaded by other people — Hardcover's users, and Open Library's. Hardcover's API documentation asks directly that apps serving their images publish a takedown policy, and Open Library's covers are user uploads too, so the fallback does not avoid it.

That page holds the draft and the checklist. The parts that need you rather than code: a designated agent (name, postal address, phone, email), registering that agent with the U.S. Copyright Office, a public URL to host the policy, and a link to it from the You tab and the App Store listing.

## What we left out

The design canvas has 18 screens. Some parts of it were not built, on purpose:

- **Inert affordances** render as disabled: Scan page, Say it.
- **Numbers with no data behind them** are omitted rather than invented: streaks, shared-shelf totals. Reading progress and page numbers used to be on this list; a saved word's page now backs both.
- **Screens with no server behind them** are omitted: camera, tutor chat, feed, discover, profile, and the offline / downloads / syncing screens.

## Tables and columns we deleted

Several tables and columns existed as groundwork and were **deleted**, not kept:

`book_word_aggregate`, `push_token`, `book.raw`, `book.topics`, `dictionary_entry.audio_url`, `word.example_sentence`, and the FTS5 index in the dictionary build.

None of them had a producer or a consumer, and each one carried real maintenance cost.

The bet: adding a column together with the feature that reads it is cheaper than keeping schema warm for a feature that may never arrive.

## Checking it still works

`bun run db:smoke` is the repo's only automated check.

It is a self-cleaning script that drives the real `appRouter` against a seeded local Postgres. It asserts what the schema enforces, not what TypeScript enforces:

- relation joins
- ownership scoping
- the partial unique index on `(user_id, book_id)`
- capture idempotency
- cascade deletes
- the Hardcover book insert-or-update
- the enrichment claim on `dictionary_entry`
- the live crowdsourced aggregate query
- the per-user request budget on `book.search`

Run `bun run db:start && bun run db:seed` first.

It calls neither Hardcover nor an AI provider. The enrichment checks assert the **unconfigured** path, which is also the failure path. They skip themselves when `AI_GATEWAY_API_KEY` is set, rather than spending money on a smoke run. The request-budget check skips itself the same way when `HARDCOVER_API_TOKEN` is set.
