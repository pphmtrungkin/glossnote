## Why tRPC, and why it is separate from Hono

The API uses [tRPC](https://trpc.io), not REST.

The idea of tRPC is type safety from server to client, without writing the types twice. You write a function on the server. The client calls it and gets full autocomplete. This works because the client imports the **type** of the server router, not its code. TypeScript does the rest.

So there is no OpenAPI file to keep up to date, and no hand-written client SDK. If you rename a field on the server, every client call shows a TypeScript error right away.

The router code lives in `packages/api`. The Hono app that receives HTTP requests lives in `apps/server`. These are separate on purpose.

Here is what each file does:

| File | Job |
| --- | --- |
| `packages/api/src/index.ts` | Creates tRPC and exports `router`, `publicProcedure` and `protectedProcedure` |
| `packages/api/src/context.ts` | Builds the per-request context. Today that is only `{ session }`, read once from Better Auth before any procedure runs |
| `packages/api/src/routers/index.ts` | The `appRouter` — one object that merges all feature routers |
| `apps/server/src/index.ts` | The only file that knows tRPC is served over Hono. It mounts `appRouter` at `/trpc/*` with `@hono/trpc-server` |

`publicProcedure` needs no login. `protectedProcedure` requires one. See [Authentication](/docs/authentication) for how that check works.

The benefit of the split: if we ever serve this API from a plain Node server or a different framework, only `apps/server` changes. `packages/api`, where all the logic lives, does not care.

## Adding a feature means adding a router file

Every feature router has the same shape:

1. Create a file in `packages/api/src/routers/`.
2. Export a `router({...})` with your procedures.
3. Merge it into `appRouter`.

There is no extra step to create an HTTP endpoint. A new procedure **is** the endpoint.

```ts
// packages/api/src/routers/index.ts
export const appRouter = router({
  healthCheck: publicProcedure.query(() => "OK"),
  book: bookRouter,
  dictionary: dictionaryRouter,
  folder: folderRouter,
  preference: preferenceRouter,
  word: wordRouter,
});
```

<Callout type="warn">
Do not add `app.get()` or `app.post()` routes to the Hono app for new features. The Expo app speaks tRPC only, so a REST endpoint would have no caller, and it would lose the shared types.
</Callout>

## The `book` router

`packages/api/src/routers/book.ts` has one procedure, `search`. It calls [Hardcover](https://docs.hardcover.app)'s GraphQL API, so the API token stays on the server.

It uses a plain `fetch`, not a GraphQL client. There is only one query, one POST body, and the response is untyped JSON anyway.

The code that converts Hardcover's response into our `book` shape is exported on its own as `mapSearchResults`. This split is on purpose:

- The `fetch` part is simple glue.
- The mapping part is what breaks when Hardcover changes their search index.

Because the mapping is a separate function, `db:smoke` can test it with a saved example response. No token, and no network call. See [Book search](/docs/book-search).

## The `dictionary` router

`packages/api/src/routers/dictionary.ts` has one procedure, `lookup`. It is the **only** code allowed to write the `dictionaryEntry` table.

It runs these steps:

1. Look for the normalized term in `dictionaryEntry`. If it is there, return it. This is what keeps the AI cost and the Datamuse quota flat: every later reader of that word is free.
2. Ask [Datamuse](https://www.datamuse.com/api/) (`?sp=<term>&md=d&max=5`) whether the word exists. If it has no exact match, return `null` without calling AI. No API key is needed before 1 January 2027. After that, a free key allows 100,000 requests per day. Datamuse asks apps to acknowledge them in their docs — this page is that acknowledgement. Their definitions come from Wiktionary and WordNet.
3. Ask the AI model for the whole entry in one call: a definition, example contexts and a usage note. Save the row, already enriched, and return it. If the model says the word is not general English, return `null`.
4. If the AI call fails, save Datamuse's definition instead, then enrich that row once with AI: example contexts and a usage note, written next to it.

### The exact-word check is the most important part

Datamuse's `sp` parameter means "spelled like". It is **fuzzy**. If you ask for a word that does not exist, it returns a *different* word instead of an empty list.

For example, asking for `sietch` returns `sketch`:

```json
[{ "word": "sketch", "score": 15046, "defs": ["n\tA rapidly executed freehand drawing. "] }]
```

If we accepted that, we would save the definition of "sketch" under the user's word "sietch". It would be silent, permanent, and in a table that other readers share.

So `pickDefinition` requires `hit.word` to be exactly equal to the term before it uses anything. `db:smoke` tests this with the exact payload above.

<Callout type="warn">
Never remove that equality check. Nothing would fail loudly; wrong definitions would just start appearing in the shared table.
</Callout>

If nothing matches, `lookup` returns `null`, not an error. Words invented for a novel are normal in a reading app. `gom jabbar` is in no dictionary, and the screen says so in plain words instead of showing a failure.

The fuzzy behaviour may be useful later. It is a ready-made "did you mean...?" for words misheard by voice input, from the same endpoint.

### The AI passes

A new term that passes the Datamuse check is defined by AI. `defineTerm` in `packages/api/src/enrich.ts` asks for the definition, the contexts and the usage note together, so it costs one call. It is saved with `source: "ai_enhanced"` and `enrichedAt` already set.

A row that came from Datamuse, or from before lookups went AI-first, is enriched once afterwards by `enrichDefinition`. That pass adds columns next to the definition and never rewrites it.

The calls are per term, never per reader:

- **An existing row** is guarded by `enrichedAt`, which is both the marker and the lock. The lock is a conditional update taken *before* the AI call, so two readers who hit the same word at the same moment buy one enrichment together, not one each.
- **A brand-new term** has no row to lock yet. Concurrent lookups of it share one in-flight request instead.
- **A word nobody can define** ("gom jabbar") is remembered, so each new lookup of it does not buy another call.

### Datamuse decides whether it is a word

A word invented for a book must not be defined. Readers look words up mid-book, so a definition drawn from the book is a spoiler.

The prompt says so, but the prompt alone is not enough. At temperature 0, Gemini defines "sietch" from *Dune* on every call, and its own usage note calls the word invented.

So Datamuse goes first, as a gate rather than a source. A word it has never heard of is never sent to the model. A word it does know still has to pass the model, because Datamuse's sources include fiction: "horcrux" is in it. When the model returns an empty definition, that answer is trusted.

Measured on 2026-09-13, with every invented word asked three times:

| Word | Datamuse | Model | Result |
| --- | --- | --- | --- |
| "ephemeral", "apricity" and six more real words | knows | defines | AI definition |
| "sietch", "gom jabbar", "kwisatz haderach", "lembas" | does not know | not asked | `null` |
| "horcrux", "dementor", "mellon" | knows | empty, 3 of 3 | `null` |

The trade-off: a word Datamuse does not know, such as brand-new slang, gets no AI definition, and the app answers from the phone's own dictionary. If Datamuse cannot be reached, the lookup fails rather than skipping the gate, with the same fallback on the phone.

A rejected word is remembered in server memory (see below), so it costs a Datamuse request and at most one AI call once per server process, not once per lookup.

<Callout type="info">
The in-flight requests and the unknown-word list live in server memory, like the rate-limit counters below. A second instance can spend its own call on the same new word, and a restart forgets the unknown words. The `ponytail:` comment in `routers/dictionary.ts` marks this.
</Callout>

Both AI calls sit behind `packages/api/src/enrich.ts` and go through Vercel AI Gateway, so the model is one `provider/model` string.

`AI_GATEWAY_API_KEY` is server-only and optional. Without it, every new term goes straight to Datamuse, and lookups work exactly as they did before AI. Any AI failure falls back the same way. AI may never turn a working lookup into a broken one.

See [AI enrichment](/docs/ai-enrichment) for the cost model, the spoiler rule in the prompts, and how to change model.

### Both proxies have a request budget

`book.search` and `dictionary.lookup` spend someone else's quota. Hardcover allows 60 requests per minute for the whole token, shared by every reader of the app. So one client stuck in a retry loop could use up everybody's quota.

Both procedures carry a per-caller limit (`packages/api/src/rate-limit.ts`):

| Procedure | Limit |
| --- | --- |
| `book.search` | 20 per minute, per user |
| `dictionary.lookup` | 60 per minute, per user |

The limit is per user, not per IP address, because both are `protectedProcedure`s. A session is the thing we can attribute a request to.

Going over the limit throws `TOO_MANY_REQUESTS`. The check runs **before** the procedure body, so an over-budget call never reaches the network.

<Callout type="info">
The counters live in server memory. So the budget is per server process, and it resets when you deploy. That is fine for one instance. If this ever runs on several instances, move the counters to Postgres or Redis. The `ponytail:` comment in `rate-limit.ts` marks this.
</Callout>

## The `folder` router

`packages/api/src/routers/folder.ts` holds everything a user does with their own folders.

| Procedure | What it does |
| --- | --- |
| `list` | All folders owned by the caller, each with its linked `book` row (`with: { book: true }`) and a `wordCount` |
| `create` | Insert a folder. It can also insert-or-update a picked Hardcover book and link it. `status` defaults to `"reading"` |
| `update` | Rename the folder, move it between `reading` / `finished` / `misc`, or both |
| `delete` | Remove a folder |

### Ownership lives in the WHERE clause

There is no separate "does this folder belong to the caller?" query before `update` or `delete`. The ownership check is part of the same statement. It uses one shared helper in `packages/api/src/ownership.ts`:

```ts
.where(ownedBy(folder, input.id, ctx.session.user.id))   // and(eq(id), eq(userId))
.returning();
return assertOwned(updated, "Folder");
```

Read it step by step:

1. `ownedBy` builds `id = ... AND userId = ...`.
2. If the folder exists but belongs to another user, zero rows match.
3. `.returning()` comes back empty.
4. `assertOwned` throws `NOT_FOUND`.

So one predicate does the security check and the update together.

We throw `NOT_FOUND`, not `FORBIDDEN`, on purpose. A caller should not learn that a row exists but belongs to someone else. From outside, both cases look the same.

<Callout type="warn">
This used to be six copies of that predicate, hand-written in three different shapes. Two of them — both `delete` procedures — returned `{ id }` without checking whether any row matched. So deleting another user's word reported success.

See the [changelog](/docs/changelog). The fix changes behaviour for any caller that relied on delete being a silent no-op.
</Callout>

### `create` does more than an insert

`create` takes the **picked search result**, not a `bookId`. A `bookId` from a client is an unvalidated foreign key, so we do not accept one.

It then:

1. Inserts or updates the `book` row, matching on `(provider, external_id)`.
2. Inserts the folder pointing at that book.
3. Turns the partial unique index on `(user_id, book_id)` into a readable `CONFLICT` error, instead of letting a raw Postgres error code `23505` reach the client.

Both points are explained in [Book search](/docs/book-search).

### `wordCount`

`wordCount` is one grouped `count()` over `word`, run next to the folder query and joined in memory. It is not a subquery per row.

The library screen and the home page both show it. A folder with no words does not appear in the group-by result at all, which is what the `?? 0` in the code handles.

## The `preference` router

`packages/api/src/routers/preference.ts` holds the reader's settings.

| Procedure | What it does |
| --- | --- |
| `get` | The caller's row, or `PREFERENCE_DEFAULTS` if they have none. Never writes |
| `update` | Insert or update. Every field is optional |

For three migrations, this table had a reader and no writer. `word.create` read the column, but nothing could change it. So the aggregate opt-out promised by the [data model](/docs/data-model) could not actually be used.

Two details are worth knowing:

- **`get` never writes.** A user who has never opened Settings has no row, and receives the same defaults the column would apply. So the settings screen can render on first launch without a write. `PREFERENCE_DEFAULTS` lives in `@better-vocab/domain`, so the router and the Postgres column default cannot disagree.
- **`update` writes field by field.** A toggle sends only the value it changed, instead of sending the whole screen back. So one device cannot overwrite a setting that another device just changed. `updatedAt` is always in the `SET` clause. That keeps the timestamp correct on the conflict path (Drizzle's `$onUpdate` only runs for a plain `UPDATE`), and it means the clause is never empty when a caller sends nothing.

`apps/native/app/(tabs)/you.tsx` is the caller.

## The `word` router

`packages/api/src/routers/word.ts` is the main capture flow. If you are new to this codebase, read this file first. Several decisions from the [data model](/docs/data-model) appear together here in real code.

| Procedure | What it does |
| --- | --- |
| `listByFolder` | Words in one folder, with the resolved `dictionaryEntry` attached |
| `search` | Search the caller's words across **all** folders. This is the server version of the offline SQLite search |
| `create` | Save one word, the moment the reader taps Save |
| `createMany` | Send the phone's offline queue in one request — see below |
| `suggestions` | Words other readers of this book saved that the caller does not have. Counts only, no definitions. An optional `prefix` narrows it to words starting with what the reader typed, which is how Add word completes a word |
| `topicWords` | AI-picked words for the folder's book, grouped by subject, minus words already in the folder — see below |
| `quiz` | Fill-in-the-blank cards over the caller's own words — see below |
| `update` | Edit the reader's note, toggle `mastered`, or stamp a review. It cannot change a definition |
| `delete` | Remove a word |

`create` and `createMany` both call one private function, `captureWord`. That is on purpose. The rules below — especially "a client never writes `dictionary_entry`" — must hold for the live save **and** for the offline flush. One function means they cannot drift apart.

Both take an optional `page`. `captureWord` stores it on the word and moves the folder's `currentPage` forward with `greatest(...)`, so an offline flush moves reading progress exactly like a live save. `folder.update` takes `currentPage` too — any page, or `null` to clear it.

Here is what `captureWord` does:

1. **Check that the folder belongs to the caller.** While reading that row, also read its `bookId`. We copy that value onto the new `word` row. (`word.bookId` is a deliberate copy; the [data model](/docs/data-model) explains why.)
2. **If a definition was sent**, store it on `word.definitionOverride`, on this user's row only. It is never written to the shared `dictionaryEntry` cache. Only server code may write that table.
3. **Read the caller's preferences** and snapshot the aggregate opt-in value onto this word. It is a snapshot, not a live reference.
4. **Insert the word** with `onConflictDoNothing` on `(folderId, normalizedTerm)`. If the word is already in this folder, nothing is inserted and the existing row is returned. This is what makes "tap a crowdsourced word to add it" safe to tap twice.

### `word.createMany` — sending the offline queue

`pending_sync` (see [Offline dictionary](/docs/offline-dictionary)) collects words saved with no signal. `createMany` receives them: up to 100 at a time, in one request.

The important part is the return shape. It reports the result **for each capture**, not one result for the whole batch:

| Status | Meaning | What the phone does |
| --- | --- | --- |
| `saved` | Written, or already there | Delete the queued row |
| `dropped` | Can never be written — for example, the folder was deleted on another device | Delete it too. Retrying will never work |
| *(thrown error)* | Temporary — lost connection, database fault | Keep the queue and try again later |

Partial success is the whole point. A folder deleted on another device must not block every other queued word. And a queue that can never empty is worse than one that drops a row and says so.

The phone's own `localId` is sent back unchanged. It means nothing on the server and is never stored. It only lets the app match each result to a queued row.

Because `captureWord` uses the same `onConflictDoNothing`, resending the whole queue after a crash is safe. Words that were already written come back as `saved` with the existing row id, instead of an error or a duplicate.

Folder ownership is read once per distinct folder, and the preference is read once for the whole batch. Neither is read per word.

The phone side is built. `apps/native/lib/pending-sync.ts` writes the queue rows and sends them; `apps/native/hooks/use-pending-sync.ts` runs the flush when the device has a connection again. See [Implementation status](/docs/implementation-status).

### `word.quiz`

A review session (UserFlow §7), built only from rows that already exist. Each card is one usage sentence with the word removed:

```
"They retreated to the ______ before the storm arrived."   → sietch
```

The sentences come from `dictionary_entry.contexts`. That row is shared and keyed by term, so **a quiz costs no AI call of its own**. Every card came from the one enrichment that term will ever get, no matter how many readers quiz on it. See [AI enrichment](/docs/ai-enrichment#contexts-and-the-fill-in-the-blank-card).

A word is left out of the deck for one of three reasons. Each one is a rule, not an accident:

| Excluded | Why |
| --- | --- |
| `mastered` | This is exactly what mastering is for. §7 asks that mastered words be deprioritized |
| No resolved `dictionaryEntry` | A word saved offline and never looked up has no sentence to blank out |
| An entry with no `contexts` | It was resolved before enrichment existed, or enrichment produced nothing usable |

Cards are ordered least-recently-reviewed first, and words never reviewed come before those. So a session starts with what the reader has seen least. `word.update({ reviewed: true })` moves a card to the back of the queue.

<Callout type="info">
The sort ends with `word.id`. This looks like decoration, but it is not.

Words written in one statement — an offline flush, or the seed script — share the same `createdAt` down to the microsecond. Without a final tiebreaker, Postgres may return them in a different order each time. The deck would then reshuffle every time the reader opens it, which reads like a bug.

`db:smoke` found exactly this on its second run.
</Callout>

Each card also carries a `state`: `new` until the word has been reviewed once, then `learning`. The colour scheme's mastery dot reads this value. (`steady` exists in the type but cannot appear here, because it means mastered, and mastered words get no cards.) The home page uses the same value for the dot next to each due word.

A card carries `usageNote` too, from the same shared row. So the reveal shows the definition and then how the word is really used. This screen and the word screen are the first readers the AI columns have had.

The answer travels with the card. This is self-study over the reader's own words, not an exam. Hiding the answer would gain nothing and would cost a network request on every reveal — on a screen that should keep working in a tunnel.

### `word.suggestions`

This is the only procedure that reads across users. It answers: "which words did other readers of this book look up, that you do not have yet?"

```sql
SELECT min(term) AS term, normalized_term, count(DISTINCT user_id)::int AS readers
FROM word
WHERE book_id = $1 AND contributes_to_aggregate
  AND user_id <> $me
  AND normalized_term NOT IN (SELECT normalized_term FROM word WHERE folder_id = $myFolder)
GROUP BY normalized_term
ORDER BY readers DESC
LIMIT 20;
```

It leaves out three things on purpose:

1. your own words
2. words already in your folder
3. **any definition text**

The app resolves each suggested term against its own local dictionary, exactly like a word the user typed.

That also makes spoiler safety structural instead of a convention. There is no column in this result that could carry a context sentence or a personal note.

Freeform folders have no book, so there is no group of readers to compare with. The procedure returns an empty list, not an error.

An optional `prefix` adds `AND normalized_term LIKE $prefix || '%'`. The prefix is normalized first, and LIKE's own `%` and `_` are escaped, so a typed `%` matches only a `%`. The add-word form sends it once two letters are typed, to complete a word from other readers' captures.

### `word.topicWords`

The add-word form's other source of new words: subject areas the folder's book draws on, each with dictionary words worth knowing. It returns `[{ topic, terms }]`, minus words already in the folder.

- **Generated once per book, for everyone.** `suggestTopicWords` in `enrich.ts` asks the model for three subjects and six words each, from the book's title, authors and description. The result is stored on `book.topicWords`, so a book costs one AI call however many readers add words to it.
- **Locked like enrichment.** `book.topicWordsAt` is claimed with a conditional update before the call, so two readers opening the form for the same new book buy one call between them. A failed call releases it.
- **Every word passes the Datamuse check** in `keepDictionaryWords`, the same check a looked-up word goes through ([Datamuse decides whether it is a word](#datamuse-decides-whether-it-is-a-word)). The prompt forbids names, invented words and anything from the plot, but a prompt is not a guarantee. If Datamuse cannot be reached, nothing is stored and a later open retries.
- **Never an error for the form.** A freeform folder, no AI key, or a failed call all return an empty list, and the form simply shows no AI section.

Measured on 2026-09-14 for the seeded *Dune* book: the first call took 1.8 s and returned "Desert ecology" (arid, xerophyte, wadi, haboob, simoom, dune), "Court politics" (fealty, vassal, appanage, chivalry, regicide, treason) and "Religious movements" (ascetic, heresy, schism, dogma, proselyte, apostasy). A repeat took 17 ms.

## The native client

`apps/native/utils/trpc.ts` turns the `AppRouter` type into something the app can call. Two pieces work together:

```ts
export const trpcClient = createTRPCClient<AppRouter>({
  links: [httpBatchLink({ url: `${env.EXPO_PUBLIC_SERVER_URL}/trpc`, ... })],
});

export const trpc = createTRPCOptionsProxy<AppRouter>({ client: trpcClient, queryClient });
```

`createTRPCOptionsProxy` lets a screen write `trpc.word.listByFolder.queryOptions({ folderId })` and pass the result straight to a React Query hook such as `useQuery` or `useMutation`. You get tRPC's type safety and React Query's caching and loading states at the same time.

`trpcClient` is exported for the one case the proxy does not fit: calling a procedure **inside** a `queryFn`.

The definition resolver does exactly that. It reads the phone's SQLite dictionary first, and only calls `dictionary.lookup` if that misses. So the whole resolution is one query with one cache entry, instead of two results the screen has to merge. See [Offline dictionary](/docs/offline-dictionary#one-resolver).
