title: Book search
description: The Hardcover GraphQL integration behind folder creation

To create a folder, the user first finds the book.

`book.search` calls [Hardcover](https://docs.hardcover.app)'s GraphQL API. The result the user picks is then written into our own `book` table by `folder.create`. It is one round trip; there is no separate "create book" step.

This is what makes crowdsourced discovery possible. Two readers of the same book point at the same `book.id` only because both picked the same Hardcover result. Without that, `word.suggestions` has nothing to group by.

## Why this must run on the server

Hardcover's documentation is clear about it:

> Queries are not allowed to run in the browser, they must be run in an environment where the token can be kept secure.

A token inside the Expo bundle can be extracted from the app binary. And the whole app shares one account's quota, so one bad client could use it all up for everyone.

So `HARDCOVER_API_TOKEN` lives in `apps/server/.env`, is validated in `packages/env/src/server.ts`, and must **never** become an `EXPO_PUBLIC_*` variable. The app calls our tRPC procedure; our server calls Hardcover. The same rule applies to every third-party key.

The token is **optional**. Without one, `book.search` returns a clean `PRECONDITION_FAILED`, and the app still works: you type a title and get a freeform folder.

That fallback is not a nice extra. It is the offline path the user flow requires. Search needs a connection; creating a folder does not.

## Rate limits shape the client code

| Limit | Free tier |
| --- | --- |
| Daily | 5,000 requests |
| Per minute | 60 |
| Burst | 10 in a row |
| Top-level `search` queries per request | **1** |

Two rules follow from this, and both are already in the code:

1. **The shelf screen debounces.** It waits with `useDebouncedValue` and only searches at two characters or more. One request per keystroke would spend the whole per-minute budget on a single search.
2. **Searches can never be batched.** A request may carry only one `search` field, so `SEARCH_QUERY` has exactly one top-level field.

Hardcover returns `RateLimit-Policy` and `RateLimit` headers on every response, so a client could slow down before hitting the wall. Nothing reads them yet. `book.search` only turns a `429` into `TOO_MANY_REQUESTS`.

We also apply our own limit: 20 searches per minute per user. See [API layer](/docs/api-layer#both-proxies-have-a-request-budget).

## The query

Hardcover's search runs on [Typesense](https://typesense.org/) and is exposed through one GraphQL field:

```graphql
query SearchBooks($query: String!, $perPage: Int!) {
  search(query: $query, query_type: "Book", per_page: $perPage, page: 1) {
    results
  }
}
```

`results` is an untyped JSON value — the raw Typesense payload, shaped like `{ found, hits: [{ document }] }`.

Hardcover documents which **fields are indexed**, but not the shape of that JSON. So `mapSearchResults` parses it loosely: `hits` must be an array, and everything inside a hit is optional. A strict schema would break whenever Hardcover deploys, not when we do.

There is one exception. A **missing `hits`** throws an error.

Why? If we accepted a missing `hits` as "no results", then "Hardcover changed their API" would look exactly like "this book does not exist". Nobody would notice until a user complained. Instead we throw, and the message includes the first 300 characters of the real payload.

| `book` column | Hardcover field | Note |
| --- | --- | --- |
| `provider` | — | Always the literal string `"hardcover"` |
| `externalId` | `document.id` | Converted to a string; the API returns either |
| `title` | `document.title` | |
| `authors` | `document.author_names` | Defaults to `[]` |
| `coverImageUrl` | `document.image.url`, else `document.isbns` | Hardcover's own cover, falling back to an Open Library link — see below |
| `description` | `document.description` | |
| `pages` | `document.pages` | One edition's page count. It scales the reading-progress bar and validates nothing |

## Covers come from Hardcover, with Open Library as the fallback

`mapSearchResults` reads Hardcover's own `image.url`. When a hit has none, `openLibraryCoverUrl` builds an [Open Library Covers API](https://openlibrary.org/dev/docs/api/covers) link from its ISBNs instead:

```
https://covers.openlibrary.org/b/isbn/9780441294671-M.jpg?default=false
```

Hardcover lists every edition's ISBN, in every language, in no useful order. So the link uses an English-edition ISBN (978-0, 978-1 or 979-8) where there is one, and ISBN-13 before ISBN-10.

- **Why Hardcover first.** On 27 real search results, Hardcover's own images covered 19, where Open Library's ISBN links covered 7. A shelf of blank tiles is the first thing a reader notices. The [changelog](/docs/changelog) records the other approaches that were measured.
- **The server makes no request.** The phone loads the image, so Open Library's ISBN limit (100 requests per 5 minutes per IP) is spent per device.
- **A missing Open Library cover is a 404, not a blank image,** because of `?default=false`. `components/book-cover.tsx` shows the title set in type when a load fails.
- **Only two hosts are stored.** `folder.create` keeps a `coverImageUrl` from `assets.hardcover.app` or an Open Library link of the shape above, and stores anything else as `null` — the `book` row is shared by every reader of that book, so one reader must not be able to put an arbitrary image on it. `db:smoke` checks it.

<Callout type="warn">
Hardcover's covers are uploaded by its users, and Hardcover asks that apps serving them publish a DMCA takedown policy. Open Library is a wiki whose covers are user uploads too. Publish one before the app is public, whichever source the covers come from.
</Callout>

## Why `provider` and `externalId` are plain text

This is the schema choice that lets us change providers without a migration.

Today `provider` is always `"hardcover"`, and `externalId` is whatever id Hardcover uses. Adding a second source, or moving off Hardcover completely, is a different string in an existing column — not an `ALTER TABLE`.

The two columns together have a unique index. That is what makes the insert-or-update safe to run twice.

## Linking a book to a folder

`folder.create` takes the picked search result, not a `bookId`:

```ts
book: z.object({ externalId, title, authors, coverImageUrl, description }).optional()
```

A `bookId` from a client would be an unvalidated foreign key from an untrusted source. By sending the search result itself, the server decides which row exists.

It inserts or updates on the unique `(provider, external_id)` pair, then inserts the folder:

```ts
.onConflictDoUpdate({ target: [book.provider, book.externalId], set: { title, authors, coverImageUrl, description } })
```

Two decisions inside that:

- **`DO UPDATE`, not `DO NOTHING`.** Hardcover adds covers and descriptions after a book is first indexed. So picking a book again refreshes old data, instead of keeping whatever we cached first. Every reader of Dune ends up on exactly one `book` row, which is what lets the crowdsourced query group correctly.
- **The insert happens inside the mutation.** If folder creation fails, no `book` row is left behind. The alternative — a separate `book.create` call from the client — leaves an orphan row every time the second step fails.

### One folder per book

`folder_userId_bookId_uidx` is a partial unique index:

```sql
UNIQUE (user_id, book_id) WHERE book_id IS NOT NULL
```

So a user may have one folder per book, and unlimited freeform folders.

Before book search existed, nothing could trigger this index. Now "add Dune twice" is a normal user action. So `folder.create` catches the Postgres error `23505` and rethrows it as `CONFLICT` with the message "You already have a folder for this book."

One trap: Drizzle wraps driver errors, so the Postgres `constraint` name is on the error's `cause`, not on its message. The `violates()` helper walks the `cause` chain instead of matching on message text.

<Callout type="warn">
Linking happens **only when the folder is created**.

There is deliberately no `folder.updateBook`. `word.bookId` is copied from `folder.bookId` at the moment a word is saved. So attaching a book to an existing folder would leave every word already in it outside the crowdsourced query.

If that feature is ever added, the same transaction must also run:

```sql
update word set book_id = ... where folder_id = ...
```
</Callout>

## What is tested, and what is not

`bun run db:smoke` covers:

- the mapping, using a saved example payload (including a hit with no cover, and numeric versus string ids)
- the insert-and-link path
- the duplicate-link conflict message
- `word.bookId` being inherited from the folder
- picking a book again reusing one row and refreshing its data

It never calls Hardcover. `mapSearchResults` is exported from `routers/book.ts` exactly so the mapping can be tested without a token and without spending quota.

So one thing is still untested: whether Hardcover's live `results` payload matches the documented shape. To check, add a token and run a real search. If the shape is wrong, the thrown error gives you the raw response.
