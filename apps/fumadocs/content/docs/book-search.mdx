---
title: Book search
description: The Hardcover GraphQL integration behind folder creation
---

Creating a folder starts by finding the book. `book.search` proxies [Hardcover](https://docs.hardcover.app)'s GraphQL API, and the result the user picks is upserted into our own `book` table by `folder.create` — one round trip, no separate "create book" step.

## Why this has to be server-side

Hardcover's own documentation settles it: *"Queries are not allowed to run in the browser, they must be run in an environment where the token can be kept secure."* A token shipped inside the Expo bundle is extractable from the app binary, and the whole app shares one account's quota — one misbehaving client could exhaust it for everyone.

So `HARDCOVER_API_TOKEN` lives in `apps/server/.env`, validated in `packages/env/src/server.ts`, and is **never** an `EXPO_PUBLIC_*` variable. The native app calls our own tRPC procedure; our server calls Hardcover. This is the same rule the software spec applies to every third-party key.

The token is **optional**. Without one, `book.search` returns a clean `PRECONDITION_FAILED` and the app still works — you type a title and get a freeform folder. That fallback isn't a courtesy, it's the offline path the user flow requires: search needs connectivity, folder creation doesn't.

## Rate limits shape the client

| Limit | Free tier |
| --- | --- |
| Daily | 5,000 requests |
| Per minute | 60 |
| Burst | 10 back-to-back |
| Top-level `search` queries per request | **1** |

Two consequences baked into the code. The shelf screen debounces through `useDebouncedValue` and only queries at two characters or more — a request per keystroke would spend the per-minute budget on a single search. And because a request may carry only one `search` field, book lookups can never be batched together; `SEARCH_QUERY` is deliberately a single top-level field.

The API returns `RateLimit-Policy` and `RateLimit` headers on every response for proactive backoff. Nothing reads them yet — `book.search` just translates a `429` into `TOO_MANY_REQUESTS`.

## The query

Hardcover's search is backed by [Typesense](https://typesense.org/), exposed through one GraphQL field:

```graphql
query SearchBooks($query: String!, $perPage: Int!) {
  search(query: $query, query_type: "Book", per_page: $perPage, page: 1) {
    results
  }
}
```

`results` is an untyped JSON scalar — the raw Typesense payload, `{ found, hits: [{ document }] }`. Hardcover documents which *fields are indexed* but not the shape of that JSON, so `mapSearchResults` parses it loosely: `hits` must be an array, everything inside a hit is permissive. An exact schema would break on Hardcover's deploys rather than ours.

The one thing it will *not* tolerate is a missing `hits`. Accepting that as optional would turn "Hardcover changed their API" into a silent "no matches found" — indistinguishable from a genuinely empty result, and invisible until a user complains. Instead it throws, with 300 characters of the actual payload in the message.

| `book` column | Hardcover field | Note |
| --- | --- | --- |
| `provider` | — | Always the literal `"hardcover"` |
| `externalId` | `document.id` | Coerced to string; the API returns it as either |
| `title` | `document.title` | |
| `authors` | `document.author_names` | Defaults to `[]` |
| `coverImageUrl` | `document.image.url` | **Optional** — see below |
| `description` | `document.description` | |

`image` is *not* in Hardcover's documented list of indexed book fields, so a cover is treated as maybe-absent rather than assumed. The shelf renders a book icon placeholder when it's null, and the smoke test asserts a hit with no image maps to `null` instead of crashing.

## Why `provider`/`externalId` are plain text

This is the schema decision that makes the provider swappable without a migration. `provider` is just `"hardcover"` today and `externalId` is whatever Hardcover calls that book's ID; adding a second source, or migrating off Hardcover entirely, is a different string in an existing column rather than an `ALTER TABLE`. The pair is uniquely indexed, which is what makes the upsert idempotent.

## Linking a book to a folder

`folder.create` takes the picked search result, not a `bookId`:

```ts
book: z.object({ externalId, title, authors, coverImageUrl, description }).optional()
```

A client-supplied `bookId` would be an unvalidated foreign key arriving from an untrusted source. Passing the hit itself means the server decides what row exists. It upserts on the unique `(provider, external_id)` pair before inserting the folder:

```ts
.onConflictDoUpdate({ target: [book.provider, book.externalId], set: { title, authors, coverImageUrl, description } })
```

`DO UPDATE` rather than `DO NOTHING` on purpose — Hardcover fills in covers and descriptions after a book is first indexed, so re-picking a book refreshes stale metadata instead of preserving whatever we happened to cache first. Every reader of Dune ends up pointing at exactly one `book` row, which is what lets the crowdsourced aggregate group correctly.

Doing the upsert *inside* the mutation also avoids an orphaned `book` row when folder creation fails — the alternative, a separate `book.create` call from the client, leaves one behind every time the second step errors.

### One folder per book

`folder_userId_bookId_uidx` is a partial unique index on `(user_id, book_id) WHERE book_id IS NOT NULL`: one folder per book per user, unlimited freeform folders. Before book search existed nothing could trigger it. Now "add Dune twice" is an ordinary user action, so `folder.create` catches the `23505` and rethrows it as `CONFLICT — "You already have a folder for this book."`

Drizzle wraps driver errors, so the Postgres `constraint` name is on the error's `cause`, not its message. The `violates()` helper walks the chain rather than matching on message text.

<Callout type="warn">
Linking happens **only at folder creation**. There is deliberately no `folder.updateBook`: `word.bookId` is snapshotted from `folder.bookId` at capture time, so attaching a book to an existing folder would strand every word already in it outside the aggregate. If that feature is ever added, the same transaction must also run `update word set book_id = ... where folder_id = ...`.
</Callout>

## What's verified, and what isn't

`bun run db:smoke` covers the mapping against a fixture payload (including a hit with no cover, and numeric vs. string IDs), the upsert-and-link path, the duplicate-link conflict message, `word.bookId` inheritance, and re-picking reusing one row while refreshing its metadata.

It never calls Hardcover — `mapSearchResults` is exported from `routers/book.ts` precisely so the mapping can be asserted without a token or a rate-limited round trip. Which means the one thing still unverified is whether Hardcover's live `results` payload matches the documented shape. Add a token and run a real search; if it doesn't match, the thrown error hands you the raw response.
