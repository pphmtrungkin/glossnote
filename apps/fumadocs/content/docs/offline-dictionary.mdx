## Why an on-device database at all

The core design principle for this app is: **offline mode should never feel broken.** If someone is reading on a plane and looks up a word, they shouldn't see a spinner that never resolves — they should get a real definition instantly, then a richer one later once they're back online. That requirement rules out "just call an API and show a loading state" as the primary path; the primary path has to be a database that already lives on the phone.

That's `expo-sqlite` — a real SQLite database bundled with (or downloaded by) the app, queried entirely on-device, no network required. It's a *separate* concept from the Postgres `dictionaryEntry` cache described in [Data model](/docs/data-model): the server-side cache is a shared, cross-user, online resource; the on-device database is a private, offline-first resource that exists purely so the app has something to answer with when there's no connection at all.

## The local tables

Defined in `apps/native/lib/local-db.ts`, created via a migration that runs through `SQLiteProvider`'s `onInit` callback (wired up in `apps/native/app/_layout.tsx`) every time the app starts. The current schema version is `user_version` 3.

`onInit` runs two steps in a load-bearing order: `migrateLocalDb` creates the schema, then `installBundledCore` merges the bundled dictionary into the `dictionary` table it just created. Both are no-ops after the first launch.

| Table | Purpose |
| --- | --- |
| `dictionary` | Every definition available on-device, in all three tiers — distinguished by a `source` column |
| `pending_sync` | Words captured offline, waiting to flush to the server once reconnected |
| `app_setting` | Device-local UI preferences (the reading theme), applied on the first frame before any session exists |

### One dictionary table, three tiers

`dictionary` started life as three separate tables — `dictionary_core`, `dictionary_extended`, and `cached_lookup` — queried as a three-hop fallthrough. They held identical columns, so they were collapsed in the `user_version` 3 migration into one table plus a `source` column:

| `source` | Meaning |
| --- | --- |
| `core` | The bundled reference dictionary, pre-populated at build time (see below). One row per term. |
| `extended` | The downloadable pack, opt-in from Settings. A term can have *multiple* rows — one per WordNet sense — ordered by `rank`. |
| `cached` | Definitions resolved online (dictionary API / AI-enhanced), kept so the same word works offline on every later lookup. |

Three payoffs. Lookup is a single indexed `SELECT` instead of three sequential queries. Dropping the extended pack becomes a `DELETE WHERE source = 'extended'` rather than a `DROP TABLE`. And `dictionary_term_source_rank_uidx`, unique on `(term, source, rank)`, both backs the lookup and makes re-merging a downloaded pack idempotent.

That last table is worth pausing on: `pending_sync` only exists on the device, never on the server. There's no equivalent "sync queue" table in Postgres, and that's intentional — the server never needs to know that a queue exists at all, it only ever sees the captures once they actually arrive. Keeping sync state purely client-side avoids having to reconcile two separate ideas of "what's pending" across two databases.

The endpoint they flush *to* now exists: `word.createMany` takes a batch and reports the outcome of each capture separately, so one dead folder can't wedge the queue ([API layer](/docs/api-layer#wordcreatemany--draining-the-offline-queue)). Nothing on the device writes to `pending_sync` or calls it yet.

## One resolver

`useDefinition` (`apps/native/hooks/use-definition.ts`) is what a screen calls when the user types or speaks a word — and it is the *only* thing a screen calls. Device tiers first, the server second, and the answer written back for next time, all behind one call.

That used to be three separate decisions: the SQL that ranked the on-device tiers, the Add Word screen that chose between device and server, and `dictionary.lookup` choosing between its cache and Datamuse. The screen was the only place that knew about both storage systems, and it reconciled their shapes by hand.

It returns a union rather than a value, so a screen renders a state instead of inferring one:

| Result | Meaning |
| --- | --- |
| `found` | A definition, plus `fromNetwork` — which is what the "Found online" / "Found in your offline dictionary" line keys off |
| `missing` | Asked everywhere available; genuinely not a word we know |
| `unreachable` | Not on the device, and the server couldn't be reached to ask |

`missing` and `unreachable` are worth keeping apart: one means "type your own definition, this is a name or an invented word", the other means "you're offline, try again later". They look identical if you only check for the absence of a definition.

Reads and writes live in `apps/native/lib/dictionary.ts`; no screen touches SQL.

### Lookup order

One query, ordered by tier:

```sql
SELECT definition, part_of_speech, example_sentence, source
  FROM dictionary
 WHERE term = ?
 ORDER BY CASE source WHEN 'cached' THEN 0 WHEN 'core' THEN 1 ELSE 2 END, rank
 LIMIT 1
```

`cached` outranks `core` deliberately. The old three-table fallthrough checked the bundled dictionary *first*, which meant a definition already resolved online — richer, possibly AI-enhanced — lost to whatever WordNet gloss shipped in the binary. Collapsing the tables made the priority a single `ORDER BY` clause, and fixed it in passing.

<Callout type="warn">
For a while that top priority was unreachable: nothing ever wrote a row with `source = 'cached'`. An online result was displayed and thrown away, so the same word cost another round trip every time. `cacheDefinition` now writes it back on every server-resolved hit — see the [changelog](/docs/changelog).
</Callout>

Within `extended`, only the top-ranked sense (`rank` 0, the most frequent) is surfaced — matching the "definition displayed instantly, user confirms" flow. The other senses stay in the table, queryable later if a "see other meanings" screen ever gets built.

## Where the bundled data comes from

The reference dictionary is built from [Open English WordNet](https://github.com/globalwordnet/english-wordnet) (CC-BY 4.0), a free lexical database of roughly 127,000 lemmas across 107,500 synsets. That's too large to ship wholesale as a "small" first-launch download, and WordNet's own data doesn't carry a "how common is this word in everyday English" signal — so the app draws a line using data WordNet *does* provide: sense frequency ranking.

**`core`** = single-word lemmas only, keeping just the #1 (most frequent) sense of each. **74,441 terms, 9.2 MB** — small enough to bundle directly in the app binary, available instantly before the app has ever touched the network.

**`extended`** = everything: every lemma including multi-word phrases, every sense, ranked. **127,311 terms across 185,129 senses, 25 MB** — downloaded separately, only if a reader opts into the larger pack from Settings.

### The build-time pipeline

Two scripts, run on a developer's machine (or CI), not on-device:

1. **`apps/native/scripts/wordnet-to-dictionary.ts`** downloads the **JSON export attached to a tagged OEWN release** (`bun run scripts/wordnet-to-dictionary.ts <out-dir> [edition]`, default `2025`) — one 9.5 MB zip, about two seconds end to end. Inside are two file groups it cross-references: ~45 "synset" files (definitions and example sentences for a category like `noun.person` or `verb.motion`) and 27 `entries-*.json` files, the lemma index, which lists every word's senses in WordNet's own frequency order. It writes two plain JSON files: `dictionary-core.json` and `dictionary-extended.json`.

   <Callout type="warn">
   Three traps, all of which this script hit for real before it produced a usable dictionary.

   **`src/sense-orders.csv` is not the lemma index.** It looks like one — `lemma,pos,synset-ids` — but it holds ~1,300 rows of manual sense-order *corrections*. Building from it yields **963 words** instead of 75,000, and nothing errors. `entries-*.json` is the vocabulary.

   **Sense rank must count across a lemma's whole entry, not per part of speech.** The device index is unique on `(term, source, rank)`, so restarting at 0 for a word's verb senses collides with its noun senses and `INSERT OR IGNORE` drops them *silently*.

   **A WordNet example is not always a string.** Attributed quotations are `{ source, text }` objects — 589 of them in the core set — which reach the SQLite driver as unbindable values.
   </Callout>

   The source is a *pinned edition* rather than `main` deliberately: reading the repo's working branch means 72 requests and a moving target. `main` had already drifted past the 2025 release when this was built — 107,528 synsets against the release's 107,519 — which is enough for two builds of "the dictionary" to be quietly different artifacts. JSON exports start at the 2025 edition; older tags ship only XML and RDF, and the script says so rather than 404-ing obscurely.
2. **`apps/native/scripts/build-dictionary-db.ts`** is intentionally *not* WordNet-specific — it just takes one of those JSON files plus a `core`/`extended` mode flag and produces a real SQLite `.db` file using Bun's built-in `bun:sqlite` (no extra dependency needed). Since both tiers now write the same `dictionary` table, the mode flag only decides the `source` value stamped on each row and whether `rank` is honoured or pinned to 0.

   It rebuilds over its output rather than opening it: `CREATE TABLE` on an existing file fails, and a half-built `.db` left behind reads as a bug in the source data.

   An FTS5 index used to be built alongside the `core` table, intended for "did you mean…" suggestions on a voice mishear. Nothing ever queried it, so it was dropped — it doubled the asset size for a feature that doesn't exist. Add it back with the suggestion UI that needs it.

## Getting the two tiers onto a device

Both tiers arrive as a pre-built SQLite file, and both land the same way — `apps/native/lib/dictionary-pack.ts` is the one module that does it.

### The merge

SQLite copies the rows itself. No JS loop:

```sql
ATTACH DATABASE ? AS pack;
INSERT OR IGNORE INTO dictionary (term, definition, part_of_speech, example_sentence, source, rank)
  SELECT term, definition, part_of_speech, example_sentence, ?, rank FROM pack.dictionary;
DETACH DATABASE pack;
```

`ATTACH` runs outside a transaction — SQLite refuses it inside one — while the `INSERT` is a single statement, so its implicit transaction covers every row: the merge lands whole or not at all. `INSERT OR IGNORE` against `dictionary_term_source_rank_uidx` is what makes a re-run idempotent rather than a duplicate-key failure. The tier is a bound parameter written *here* rather than read out of the file, so a pack built with the wrong mode can't file itself under another tier. Measured on the real files: **74,441 core rows in 86 ms, 184,356 extended rows in 272 ms.**

<Callout type="info">
A column list, not `SELECT *`. A future column added to the local table would otherwise shift the pack's values silently into the wrong ones.
</Callout>

### `core` — bundled, merged on first launch

`assets/dictionary/core.db` ships inside the binary (`db` is registered in `metro.config.js`'s `assetExts`, or Metro treats it as source). `installBundledCore` merges it from `SQLiteProvider`'s `onInit`, after the schema migration and guarded by an `app_setting` flag so a 75k-row copy doesn't run on every launch. Failures are swallowed — an app that can't open its own asset should still start, and the online tier still resolves.

<Callout type="warn">
It is deliberately **not** handed to `SQLiteProvider` as `assetSource`, which was the original plan and is a trap. The asset carries only the `dictionary` table, but the build script stamps `PRAGMA user_version = 3` on it — so `migrateLocalDb` returns early and never creates `pending_sync` or `app_setting`. A device that opened the asset directly would throw on the first theme save. Merging costs one copy of the rows and keeps `local-db.ts` the only owner of the schema; it also works on upgrade, where `assetSource` does nothing because the database already exists.
</Callout>

### `extended` — downloaded, then permanent

The download needs a connection. Nothing after it does.

`EXPO_PUBLIC_DICTIONARY_PACK_URL` points at the pack as a **plain static file** — a GitHub release asset, R2, any static host. Deliberately not served by `apps/server`: tRPC is the wrong transport for a 25 MB binary, and a static host keeps the download working when the API is down. It's optional, and Settings says the pack is unavailable rather than offering a dead button when it's unset.

`installPack` fetches it with `expo-file-system`'s `File.createDownloadTask` (progress, pause and resume come with the task), merges it, and deletes the downloaded file in a `finally` — the merged rows are the artifact, the file was a courier. `removePack` gives the space back with `DELETE FROM dictionary WHERE source = 'extended'`, which is the whole reason the three tier tables were collapsed into one.

The install's row count and byte size are recorded in `app_setting` rather than recomputed: `count(*) WHERE source = 'extended'` can't use the `(term, source, rank)` index — `source` isn't its prefix — so reporting the size would scan the table.

`app/settings.tsx` drives both halves. Installing also sets `preference.offlineDictionaryTier` to `extended`, because the *pack* is per-device while the *preference* is per-account: it's what tells a new phone to fetch it too.

## When the device has no answer

The bundled pack holds single English words, one sense each, so a phrase, a name, or a coinage will miss — *sietch* is not in WordNet, and shouldn't be. `useDefinition` then calls `dictionary.lookup` on the server, which asks Datamuse and caches the result for every other user ([API layer](/docs/api-layer#the-dictionary-router)) — and writes it into this device's `cached` tier on the way back, so the *next* lookup of that word needs no signal at all.

The order matters and is deliberate: **the device looks first, the network second.** Common words never reach the network at all. A measured lookup of "ephemeral" took 590 ms the first time and 4 ms once cached; a bundled hit takes neither.

Suggestion rows are the exception, and they opt out explicitly with `useDefinition(term, { online: false })`. A list resolving one term per row would otherwise fire a request per visible row to fill in text the reader hasn't asked for.

If both miss, that is a real answer rather than a failure. Words invented for a novel exist in no dictionary, and the screen says so.
